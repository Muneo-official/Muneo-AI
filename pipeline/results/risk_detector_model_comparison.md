# 리스크 진단 Vision 파싱 모델 교체 — Sonnet 4.6 → Sonnet 5.5

## 배경

리스크 진단(`POST /risk-detector/analyze`)의 비용은 대부분 Vision 파싱 출력 토큰이다(S3 요청당 $0.206, 출력 76%).
응답시간 병렬화([`risk_detector_latency_optimization.md`](risk_detector_latency_optimization.md)), 출력 스키마 축소
([`risk_detector_cost_optimization.md`](risk_detector_cost_optimization.md)), 이미지 해시 캐시
([`risk_detector_image_cache.md`](risk_detector_image_cache.md))까지 적용한 뒤 남은 가장 큰 레버는 모델 단가였다.

| 모델 | 입력 / 출력 ($/1M, 2026-09-25 기준) | 토큰이 같다면 |
|---|---|---:|
| `claude-sonnet-4-6` (기존) | $3 / $15 | — |
| `claude-sonnet-5-5` | $2 / $10 | −33% |
| `claude-haiku-4-5` | $1 / $5 | −67% |

## 방법

**정답으로 채점한다.** 스키마·프롬프트를 조금만 바꿔도 경계 공종 분류가 뒤집히는 걸 이전 작업에서 확인했다. 그래서 "기존
모델과 같은가"가 아니라 사람이 확정한 정답으로 채점했다(`scripts/bench/grade_truth.py`). 정답 파일은 실행마다 분류가
흔들리던 항목들이다(S1 16개, S3 22개). 공종 정의가 코드베이스 안에서 엇갈리는 3개(폐기물처리 2, 도어 1)는 채점하지 않았다
(아래 "측정하며 발견한 것").

**S3를 여러 번 잰다.** 기존 모델의 S3 정답률은 같은 코드에서도 실행마다 27%~82%로 흔들렸다. 3회로는 운에 따라 결과가
갈릴 수 있어 S3는 5회 재고 중앙값으로 판정했다.

**기준을 측정 전에 정한다.** 아래 기준을 측정 전에 확정하고, 모두 만족할 때만 채택하기로 했다.

**요청 형식.** 세 모델 모두 같은 출력 스키마·지시문·이미지 전처리를 쓴다. Sonnet 5.5만 API 제약 때문에 다르다.
- 강제 도구 호출(`tool_choice: tool`)이 400이라 `auto`로 보낸다. 도구 대신 글로 답하면 1회 재시도한다.
- 기본으로 켜진 thinking은 `between_tools`로 끈다. 표를 옮겨 적는 데 생각은 필요 없고, 생각 토큰은 출력으로 과금된다.
- 거부 대체 `fallbacks: "default"`를 켠다(Anthropic 권장 기본값).
- `strict`는 켜지 않았다. 스키마가 바뀌면 비교 변수가 하나 더 생긴다.

벤치 서버에 `--model` 옵션을 추가해 코드를 되돌리지 않고 같은 코드에서 모델을 바꿔 쟀다.

## 결과

**Haiku 4.5는 탈락.** 도구는 불렀지만 `is_estimate: false`로 답해 항목 41개가 전부 버려졌다. 41개 모두 공종 목록의 첫 값
"도배"로 분류됐고, 한글도 잘못 읽었다("도기공사"→"노기공사", "철거/보양"→"설거/보장"). 한글 표 인식 자체가 안 돼 본 측정을
생략했다.

**Sonnet 5.5 + 분류 규칙(아래)은 기준을 모두 통과했다.** 기존 운영(Sonnet 4.6) 값은 기존 측정을 같은 정답으로 다시 채점한 것이다.

| 기준 (측정 전 확정) | 기존 (Sonnet 4.6) | Sonnet 5.5 | 판정 |
|---|---|---|---|
| S1 정답 완전 일치 (28행, 7,386,000원) | 3/3 | 3/3 | 통과 |
| S1 정답 항목 (16개) | 100% | 3회 모두 100% | 통과 |
| S3 정답률 중앙값 (22개) | 82% (7회: 82·82·82·82·68·27·82) | **100%** (5회: 100·100·100·100·91) | 통과 |
| 필름시공 → 필름 분류 | 전 회차 | 5/5 | 통과 |
| 도구 미호출 | 0 | 0 | 통과 |
| S3 요청당 비용 | $0.206 | **$0.138 (−33%)** | 통과 |

| 기준 밖 지표 | 기존 (Sonnet 4.6) | Sonnet 5.5 |
|---|---|---|
| S1 비용 / 응답시간 | $0.0335 / 25.5s | $0.0243 (−27%) / 11.4s |
| S3 응답시간 중앙값 | 62.9s | **19.7s (−69%)** |
| S3 정답률 최저 | 27% | 91% |
| S3 금액 합계 범위 | 8,424만~8,757만 원 | 8,381만~8,541만 원 |

더 싸고, 3배 빠르고, 정확하고, 실행마다 덜 흔들린다. 입력 토큰은 S3 기준 +14%(규칙 문장 + 토크나이저 차이)지만 단가가
2/3라 비용이 33% 줄었다. 남은 오답은 1회에서 나온 목공→창호 2개로, 기존 모델도 같은 경계에서 틀린 적이 있다.

측정 파일: `logs/bench/latency_eval2-sonnet55-s1_20261001_013924.json`(S1 3회),
`latency_eval2-sonnet55-s3_20261001_015758.json`(S3 5회). 모델 비교 전체 API 비용 약 $1.7.

## 측정하며 발견한 것

**1. Sonnet 5.5는 항목 내용 기준, 기존 모델은 섹션 제목 기준으로 분류한다.** 본 측정 전에 S1 1회로 요청 형식을 확인하는
스모크 측정을 세 차례 했다. 1차에서 5.5는 항목·금액을 모두 맞혔지만 "수전공사(수전,욕실)" 섹션의 12개를 욕실로 분류했다
(정답 설비). 파티션·선반·환풍기처럼 욕실 부속이 수전공사 섹션 아래 적혀 있었는데, 5.5는 항목 내용대로, 기존 모델과 정답은
섹션대로 분류한 것이다. 2차에서 "수전 항목만 설비" 규칙을 넣자 5.5는 수전 2개만 설비로 옮기고 부속 10개는 욕실에 뒀다.
3차에서 규칙을 섹션 단위로 넓혀 정답에 맞췄다(이 규칙은 재검토 예정, 아래 한계 참고).
- 수전공사 섹션의 항목 → 설비 (`RISK_FAUCET_CATEGORY_RULE`)
- 도기공사 섹션의 항목(양변기·세면대·욕조와 그 섹션의 방수·부자재·인건비) → 욕실 (`RISK_TOILET_CATEGORY_RULE`)

**2. 첫 판정은 공종 정의에 좌우되고 있었다.** 규칙 적용 후 첫 본 측정에서 5.5의 S3 오답 7개가 모두 정의가 엇갈리는 항목이었다.
도기 4개, 폐기물처리비 2개, ABS 도어 1개다. 폐기물·도어는 5.5가 오히려 정규화 표·누락 룰과 일치했다. 정의 하나로 승패가
갈리는 비교는 의미가 없어서, 결과를 확정하지 않고 정의부터 정리했다.
- **도기 = 욕실로 결정.** 실제 코퍼스(estimate_cases 709건)를 품명으로 세어 보니 양변기·세면기는 욕실 905 vs 설비 약 650으로
  욕실이 다수였다. 리스크 누락 룰·가견적 엔진도 욕실이다. 정규화 표(`pipeline/categories.py`)만 "도기공사 → 설비"였다.
- **폐기물처리·도어는 채점 제외.** 스키마 설명·정규화 표·누락 룰이 서로 달라 공종 정의 통일 작업(#62)으로 넘겼다.

**3. 기존 모델은 같은 견적서에서 도기를 철거로 분류하기도 했다.** 도기공사 섹션을 S1에서는 욕실로, S3에서는 철거로 분류했다.
어떤 정의로 봐도 틀린 분류다. 실행마다 설비↔욕실, 목공↔창호가 통째로 뒤집혀 정답률이 27%까지 떨어진 실행도 있었다.

## 운영 반영 시 달라지는 점

**분류 규칙** (리스크 진단 파싱 스키마만 바뀌고, 크롤링 수집 스키마는 그대로)
- 수전공사 섹션은 설비, 도기공사 섹션은 욕실로 일관되게 분류된다.
- 공종별 합계가 달라지므로 가격 이상 탐지(설비·욕실)와 누락 판정 결과가 바뀔 수 있다.
- 스키마가 바뀌어 이미지 파싱 캐시의 버전 키가 바뀐다. 배포 후 같은 이미지를 처음 다시 올리면 한 번 새로 파싱되고(비용 1회)
  이전과 결과가 다를 수 있다. 그 뒤로는 다시 고정된다.

**모델 교체**
- 도구 대신 글로 답한 호출은 정상 종료(`end_turn`)일 때만 한 번 재시도한다. 거부(`refusal`)와 출력 한도(`max_tokens`)는
  다시 보내도 같은 결과라 제외한다. 재시도 후에도 도구를 안 부른 청크가 있으면 그 이미지는 파싱 캐시에 저장하지 않는다
  (불완전한 결과가 재업로드마다 고정되지 않게). 로그 `risk_vision_call`에 `retried`·`stop_reason`·`served_model`.
- 거부 대체는 Sonnet 5.5에서 "cyber"·"frontier_llm" 거부만 대상이다. Claude API 전용이라 Bedrock·Vertex로 옮기면 빼야 한다.
- Sonnet 5.5는 Sonnet 4.x와 별도의 rate limit을 쓴다. 운영 트래픽 전에 조직 한도를 확인한다.
- 모델명과 요청 형식(tool_choice·thinking·fallbacks)도 캐시 버전 키에 들어 있어 교체 시 캐시가 한 번 초기화된다.

## 한계

- 기존 모델 값은 다른 날(9/29~9/30) 측정한 데이터다.
- 표본이 작다(S1 3회, S3 5회). S2는 정답 항목이 2개뿐이고 기존 전 회차 100%라 재지 않았다.
- 정답 파일은 실행마다 흔들리던 항목만 담고 있어 전체 항목의 정확도는 아니다. 행 누락·금액은 S1 정답 일치와 항목 수·합계로
  따로 확인했다.
- **수전공사 섹션 규칙은 재검토 예정이다.** 정답 기준(2026-09-29 확정 "수전공사 섹션 → 설비")에 맞춘 임시 규칙이라, 샤워
  파티션·환풍기 같은 욕실 부속까지 설비로 보낸다. 실제 코퍼스는 욕실 부속을 설비·욕실로 거의 반반 섞고 있고, 현장 관행과
  리스크 누락 룰은 욕실 쪽이다(설비 = 배관·급배수·수전, 욕실 = 도기·욕실 부속). 코퍼스 재집계와 함께 공종 정의 통일
  작업(#62)에서 바로잡는다.
