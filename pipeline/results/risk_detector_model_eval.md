# 리스크 진단 Vision 파싱 모델 비교 — Sonnet 4.6 vs Sonnet 5.5 vs Haiku 4.5

## 배경

리스크 진단 비용의 76%가 출력 토큰이다(S3 요청당 $0.206, 출력 약 10,500토큰). 응답시간(병렬화)·출력 스키마 축소·
이미지 해시 캐시까지 적용한 뒤 남은 가장 큰 레버는 모델 단가다(claude-api 스킬 모델표, 2026-09-25 기준).

| 모델 | 입력 / 출력 ($/1M) | 토큰이 같다면 |
|---|---|---:|
| `claude-sonnet-4-6` (현재) | $3 / $15 | — |
| `claude-sonnet-5-5` | $2 / $10 | −33% |
| `claude-haiku-4-5` | $1 / $5 | −67% |

스키마·프롬프트를 조금만 바꿔도 경계 공종 분류가 흔들렸으므로([`risk_detector_cost_optimization.md`](risk_detector_cost_optimization.md)),
모델 비교는 "현재 모델과 같은가"가 아니라 사람이 확정한 정답(`logs/bench/category_truth.json`, 40개 항목)으로 채점한다
(`scripts/bench/grade_truth.py`).

## 요청 형식 차이

- 세 모델 모두 같은 출력 스키마(`RISK_ESTIMATE_TOOL`)·지시문·이미지 전처리를 쓴다.
- Sonnet 5.5는 강제 도구 호출(`tool_choice: tool`)이 400이라 `auto`로 보내고, 기본으로 켜진 thinking은
  `between_tools`로 끈다(생각 토큰이 출력으로 과금되지 않게). strict는 켜지 않는다 — 스키마가 바뀌면 변수가 늘어난다.
  도구 대신 글로 답한 호출은 `tool_called=false`로 기록한다.

## 현재 모델 기준값 (새 채점 스크립트로 기존 결과 재채점, API 호출 없음)

| 케이스 | 정답 항목 | Sonnet 4.6 정답률 |
|---|---:|---|
| S1 | 13 | 3회 모두 100% |
| S2 | 2 | 3회 모두 100% |
| S3 | 25 | 7회: 80 / 76 / 80 / 80 / 60 / 28 / 76% (중앙값 76%) |

S3는 같은 코드·모델에서도 실행마다 28%~80%로 흔들린다(설비↔철거, 목공↔창호가 통째로 뒤집히는 실행이 있음).
그래서 3회 측정으로는 운에 따라 합격·탈락이 갈릴 수 있어, S3는 5회 재고 중앙값으로 판정한다.
(이전 문서의 "82%"는 채점 범위가 달라 이 기준과 직접 비교하지 않는다.)

## 1차 스모크 (2026-09-30, S1 1회, 기존 스키마)

| | Sonnet 4.6 (기존 측정) | Sonnet 5.5 | Haiku 4.5 |
|---|---|---|---|
| 비용 | $0.0335 | $0.0231 (−31%) | $0.0169 (−50%) |

- 요청 형식은 두 모델 모두 문제없음 (200, 도구 호출).
- **Haiku 4.5 탈락:** 도구는 불렀지만 `is_estimate: false`로 답해 항목 41개가 전부 버려졌고, 41개 모두 enum 첫 값
  "도배"로 분류, 한글 오독("도기공사"→"노기공사", "철거/보양"→"설거/보장"). 한글 표 인식 자체가 안 돼 본 측정 생략.
- **Sonnet 5.5:** 항목·금액은 정답이지만 수전공사 12개를 전부 "욕실"로 분류(정답 "설비" — 코퍼스 정규화 규칙).
  같은 방향 12개라 노이즈가 아닌 체계적 차이 → 기존 스키마로는 "S1·S2 100%" 기준 불합격.

## 2차: 수전 규칙 추가

필름 규칙과 같은 방식으로 공종 설명에 한 줄 추가(`RISK_FAUCET_CATEGORY_RULE`):
"수전(수도꼭지) 교체·설치 공사는 욕실·주방 어디에 달리든 '설비'로 분류한다." 도기(양변기·세면대)는 대상 아님.

스키마가 바뀌므로 Sonnet 4.6 기준값도 새 스키마로 다시 잰다(두 모델을 같은 조건에서 비교). 채택 기준은 본 측정 전에
새로 확정한다.

**2차 스모크 (S1 1회):** Sonnet 4.6 92%(12/13), Sonnet 5.5 23%(3/13).
- Sonnet 5.5는 규칙대로 진짜 수전 2개(세면기·샤워 수전)를 설비로 옮겼다. 틀린 10개는 수전이 아니라 "수전공사(수전,욕실)"
  섹션에 있는 욕실 부속(샤워 파티션·슬라이딩장·선반·액세서리·SMC 천정·환풍기·부자재·인건비)이다. 5.5는 항목 내용 기준,
  정답(D1)과 Sonnet 4.6은 섹션 기준. 규칙을 "수전 항목"으로 좁게 쓴 게 정답 근거("수전공사 섹션 → 설비")와 어긋났다.
- Sonnet 4.6은 새 오답 1개: "씽크대,욕실1개소"(철거/보양 섹션) → 공과잡비. 규칙 전 3회는 모두 철거였다. 규칙의 부작용인지
  실행 간 변동(알려진 철거↔공과잡비 경계)인지는 1회로 구분 불가.

## 3차: 수전공사 섹션 규칙

규칙을 섹션 단위로 교체: "견적서에 '수전공사' 또는 '수전/위생공사' 구분(섹션)이 있으면, 그 섹션에 속한 항목은 수전뿐 아니라
샤워 파티션·선반·액세서리·환풍기·천정재·부자재·인건비까지 모두 '설비'로 분류한다."

일반 섹션 규칙("항목은 속한 섹션의 공종으로")은 쓰지 않았다. 기존 공종 설명이 "실제 작업 내용을 보고 매핑"하라고 하고
"폐기물처리 → 공과잡비"로 적혀 있는데, 코퍼스 정규화 표(`pipeline/categories.py`)는 폐기물처리 섹션 → 철거, 도기공사 섹션 →
설비다. 일반 규칙은 이 충돌을 건드리고, 정답 파일에 없는 항목(보양·폐기물처리비·도기)까지 옮겨 채점으로 잡히지 않는 변화를
만든다. 이 불일치 자체는 별도 과제로 남긴다.

**3차 스모크 (S1 1회):** 두 모델 모두 정답 100%(13/13), S1 일치, 도구 미호출 0. Sonnet 4.6의 철거 오답은 재현되지 않아
2차의 오답은 실행 간 변동으로 본다. 비용 4.6 $0.0339 / 5.5 $0.0251(−26%), 응답시간 25.5s / 12.1s.

정답 파일 밖의 차이: 도기공사 섹션(세면도기 16.5만·양변도기 18.5만 원)을 4.6은 욕실, 5.5는 설비로 분류했고, 그 때문에
4.6에만 "설비 항목 가격이 시세 범위를 벗어남" 이슈가 났다(리스크 이슈 3개 vs 2개). 도기를 어느 공종으로 볼지는 코드베이스
안에서도 갈려 있어(아래 후속 과제) 이번 비교에서는 채점하지 않고 관찰로만 기록한다 — 어느 쪽으로 정하든 그 정의 하나가 모델
비교의 승패를 정해버린다.

## 후속 과제: 욕실·설비 공종 정의 불일치

같은 항목을 코드베이스가 서로 다른 공종으로 본다.

| 위치 | 도기(세면대·양변기) | 수전공사 | 역할 |
|---|---|---|---|
| `pipeline/categories.py` (CATEGORY_NORM) | 설비 | 설비 | 가격 비교 코퍼스(estimate_cases `cost_*`) 정규화 |
| `app/domain/risk_constants.py` | 욕실 | 설비·욕실 양쪽 | 리스크 진단 공종 매핑 |
| `app/domain/risk_analyzer.py` | 욕실 키워드 | — | 누락 체크 룰 |
| `app/domain/estimate_engine.py` | 욕실 | 욕실 | 가견적 생성 |
| `pipeline/tool_schema.py` 공종 설명 | "작업 내용 기준" | 섹션 규칙으로 설비 | 파싱 |

또 공종 설명은 "폐기물처리 → 공과잡비"인데 CATEGORY_NORM은 "폐기물처리 → 철거"다. 파싱·룰·코퍼스가 다른 기준을 쓰면
가격 이상 탐지가 가짜 이슈를 내거나 누락 판정이 흔들린다. 하나의 기준을 정하고 세 곳을 맞추는 별도 작업으로 다룬다.

## 본 측정

결정할 것은 "현재 운영(Sonnet 4.6 + 기존 스키마)" vs "후보(Sonnet 5.5 + 수전공사 섹션 규칙)"다. "4.6 + 새 스키마"는
운영에 나갈 일이 없으므로 재지 않는다 — 5.5가 통과하면 5.5 + 새 스키마로 가고, 탈락하면 수전 규칙까지 되돌려 현재 운영을
유지한다(4.6에 측정 안 한 규칙만 얹지 않는다).

- 기준값: 현재 운영의 기존 측정 — S1 3회(`latency_cost_b2_film_20260929_171820`), S3 7회(위 "현재 모델 기준값").
- 후보: Sonnet 5.5 S1 3회(3차 스모크 1회 + 추가 2회), S3 5회. S2는 정답 항목이 2개뿐이고 전 회차 100%라 제외.
- 예상 비용 약 $0.81.
- 한계: 기준값은 다른 날(9/29~9/30) 잰 데이터다.

### 정정: 이 판정은 공종 정의에 달려 있었다 (2026-10-01)

S3의 5.5 오답 7개가 모두 정의가 엇갈리는 항목이었다 — 도기공사 섹션 4개(정답 설비, 5.5는 3/5회 설비·2/5회 욕실),
폐기물처리비 2개(정답 공과잡비 D2, 5.5는 철거 — 정규화 표·누락 룰과 일치), ABS 슬라이딩도어 1개(정답 목공 D3, 5.5는 창호 —
정규화 표 "도어공사 → 창호"와 일치). 위 "채택"은 이 정의를 전제로 한 결과라 그대로 확정하지 않는다.

**도기 = 욕실로 결정 (D4).** 실제 코퍼스를 세어 보니(estimate_cases 709건, 읽기만) 양변기·세면기 항목은 욕실 905 vs 설비
약 650으로 욕실이 다수였고(D1의 "코퍼스는 설비" 전제는 정규화 표만 본 것), 리스크 누락 룰·가견적 엔진도 욕실이다. 코퍼스
594건은 공종이 정규화 값으로만 남아 원래 섹션 이름이 없지만 품명이 남아 있어, 재집계는 API 없이 가능하다(후속 과제).

정답 파일 변경(`category_truth.json`, 백업 `category_truth.backup-20261001.json`): S3 도기 4개 설비 → 욕실, S1 도기공사 섹션
3개(세면도기·양변도기·욕조자리) 욕실로 추가, 폐기물 2개·도어 1개는 `disputed`로 표시해 채점 제외(`grade_truth` 기본값).

## 운영 반영 시 달라지는 점

**수전·도기 섹션 규칙 (리스크 진단 파싱 스키마만, 크롤링 수집 스키마는 그대로)**
- 수전공사 섹션 항목(수전뿐 아니라 파티션·선반·액세서리·환풍기·인건비)은 설비, 도기공사 섹션 항목(양변기·세면대·욕조와
  그 섹션의 방수·부자재·인건비)은 욕실로 일관되게 분류된다. 예: S1은 설비 136만 원·욕실 45만 원으로 매번 같게 나온다.
- 공종별 합계가 달라지므로 가격 이상 탐지(설비·욕실)와 누락 판정 결과가 바뀔 수 있다. 도기가 욕실에 남아 누락 룰의
  "욕실 필수 항목(양변기·세면·도기)"과 맞는다.
- 가격 비교 코퍼스는 아직 도기가 욕실·설비로 섞여 있다(약 58:42). 코퍼스를 재집계하기 전까지 설비·욕실 가격 비교는 흔들릴
  수 있다(후속 과제).
- 스키마가 바뀌어 이미지 파싱 캐시의 버전 키가 바뀐다. 배포 후 같은 이미지를 처음 다시 올리면 한 번 새로 파싱되고(비용 1회),
  이전과 결과가 다를 수 있다. 그 뒤로는 다시 고정된다.

**모델 교체 (Sonnet 4.6 → 5.5)**
- 요청 형식: 도구 호출 `auto`, thinking `between_tools`(끔), 거부 대체 `fallbacks: "default"`(베타 `server-side-fallback-2026-07-01`,
  Claude API 전용 — Bedrock·Vertex로 옮기면 빼야 한다).
- 도구 대신 글로 답한 호출은 한 번 재시도한다(거부는 제외). 로그 `risk_vision_call`에 `retried`·`stop_reason`·`served_model`.
- Sonnet 5.5는 Sonnet 4.x와 별도의 rate limit을 쓴다 — 운영 트래픽 전에 조직의 한도를 확인한다.
- 모델명이 캐시 버전 키에 들어 있어 교체 시에도 캐시가 한 번 초기화된다.
