# 리스크 진단 Vision 호출 비용 절감 — 결과

## 배경

리스크 진단(`POST /risk-detector/analyze`) 요청 1건당 Anthropic API 비용이 높다는 문제가 있었다.
응답시간 개선(병렬화, [`risk_detector_latency_optimization.md`](risk_detector_latency_optimization.md))
때 넣은 계측으로 요청당 비용을 재 보니 **비용의 약 80%가 출력 토큰**이었다. 견적서 항목마다
`code`·`category`·`description`·`unit_price`·`quantity`·`unit`·`amount` 7개 필드를 생성하는데,
출력 토큰 단가가 입력의 5배다(`claude-sonnet-4-6` 입력 $3 / 출력 $15 per 1M, 2026-09-27 기준).

| 케이스 | 청크 수 | 입력 토큰 | 출력 토큰 | 요청당 비용 | 출력 비중 |
|---|---:|---:|---:|---:|---:|
| S1 | 1 | 3,384 | 2,479 | $0.047 | 79% |
| S2 | 2 | 7,046 | 6,942 | $0.125 | 83% |
| S3 | 5 | 15,639 | 13,646 | $0.252 | 81% |

## 무엇을 줄일지 — 필드별 사용처 조사

리스크 판정은 모델이 아니라 파싱 후의 룰·통계(누락/중복/모호 표현/단가 누락/양중비/가격 이상)가 한다.
그래서 "모델이 어떤 필드를 내주는가"가 곧 "룰이 무엇을 판정할 수 있는가"다. 코드를 따라가며 필드별
사용처를 정리하고, 코퍼스 571건에 필드를 뺀 채 실제 병합·룰을 돌려 영향을 확인했다(API 호출 없음).

| 필드 | 사용처 | 결정 |
|---|---|---|
| category, description, amount | 공종 분류, 누락·중복·모호, 가격 체크, 리포트 | 유지 |
| unit_price | **단가 누락 룰의 유일한 트리거** (amount 없는 항목은 병합 단계에서 이미 버려짐) | 유지 — 빼면 단가 누락 이슈가 575 → 38,227건으로 폭증 |
| code | 청크 중복 제거 키에서 **행 식별자** | 유지 — 빼면 571건 중 243건에서 서로 다른 행이 합쳐져 사라짐 |
| quantity | 단가·금액 열 뒤바뀜 보정의 입력 | 제거 — 실측 원본 출력 941개 항목에서 보정이 한 번도 필요 없었음 |
| unit | 사용처 없음 | 제거 |

크롤링 수집(배치) 경로도 같은 스키마를 쓰지만, 수집 데이터는 가견적 코퍼스가 되므로 **리스크 진단
전용 스키마를 분리**하고 수집 스키마는 그대로 뒀다.

## 측정하며 발견한 것

필드를 빼자 모델 출력이 예상하지 못한 방식으로 바뀌었다. 실측 원본 출력을 청크 단위로 캡처하도록
벤치를 확장해 원인을 하나씩 추적했다.

1. **한 청크에서 `code`를 통째로 생략** (3/3회, 0/72개). 청크마다 `code` 유무가 다르면 중복 제거 키가
   달라져 청크 겹침 구간의 행이 두 번 남았다(S3 항목 +3~6개, 금액 +1~3백만 원) → `code`를 필수 필드로 지정
2. **애매한 항목의 공종 분류가 뒤집힘**. `unit` 하나만 빼도 발생 — 필드 개수가 아니라 요청이 조금만
   달라져도 경계에 있는 항목(설비↔욕실, 철거↔공과잡비)의 분류가 흔들리는 민감성이었다. 이 중 명확히
   틀린 방향은 "필름시공(샷시,문,틀…)"을 창호로 분류한 것 하나였고, 이 때문에 "필름 가격 이상" 이슈가
   사라졌다 → 공종 설명에 필름 규칙 한 줄 추가(가격 체크 코퍼스의 정규화 규칙 시트공사→필름과 같은 내용)
3. **"기준과 같은가"로는 분류를 판정할 수 없다**. 기준(기존 스키마)도 세면기·양변기를 철거로 분류하는 등
   틀린 곳이 있어서, 흔들린 항목 40개에 견적서 섹션과 코퍼스 규칙으로 정답을 붙여 "맞는가"로 채점했다

## 변경 내용

- 리스크 진단 전용 출력 스키마 `RISK_ESTIMATE_TOOL` (`pipeline/tool_schema.py`)
  - `ESTIMATE_TOOL`에서 파생: `unit`·`quantity` 제외, `code` 필수, 공종 설명 끝에 필름 규칙 한 줄
  - 리스크 진단의 비동기 호출(`acall_vision_api_with_usage`)만 사용. 수집 배치·동기 호출은 기존 스키마
- 벤치 확장 (`scripts/bench/`)
  - 벤치 서버가 청크별 원본 모델 출력과 룰 입력 항목을 캡처 (병렬 호출이라 이미지 해시로 청크 식별)
  - `accuracy.py`: 기준 실행 간 변동 범위 + 허용폭(항목 수 ±3%, 공종별 금액 ±5%, 비중 ±3%p, 합계 ±2%) 판정
  - `--risk-schema full`: 같은 코드로 기존 스키마(기준)와 새 스키마를 번갈아 측정

## 결과 (실제 API, 케이스당 3회, 중앙값)

| 케이스 | 청크 수 | 출력 토큰 | 요청당 비용 | wall p50 |
|---|---:|---:|---:|---:|
| S1 | 1 | 2,487 → 1,534 | $0.047 → $0.034 (**−29%**) | 34.1s → 25.5s |
| S2 | 2 | 6,942 → 5,013 | $0.125 → $0.097 (**−23%**) | 58.8s → 47.8s |
| S3 | 5 | 13,661 → 10,502 | $0.252 → $0.206 (**−18%**) | 71.5s → 62.9s |

출력이 줄어든 만큼 호출 한 번의 시간도 줄어 응답시간이 같이 짧아졌다. 동시 호출 상한이 처리량을
정하는 구간(동시 10명 이상)에서는 호출 시간 단축이 곧 처리량 증가다.

**정확도**
- S1은 이미지와 한 줄씩 대조해 두 스키마 모두 정답과 완전히 일치(28행, 합계 7,386,000원)
- 분류가 흔들린 40개 항목의 정답 채점: 기존 스키마 60% → **새 스키마 82%**
- 필름 가격 이상 이슈: 기존 3/3회 → 새 스키마 3/3회 (필름 규칙 없이 필드만 뺐을 땐 0/3회)

측정 순서와 채택 기준은 측정 전에 정해 두고 지켰다: 필름시공이 필름으로 분류(3회 중 2회 이상)되고,
정답 채점이 기존 스키마 이상이면 채택.

## 한계

- 테스트셋이 3케이스(견적서 4장)이고, 정답은 분류가 흔들린 40개 항목에만 붙였다. 8청크 케이스는 예산상 제외
- 수전·도기 섹션 항목의 정답을 "설비"로 둔 것은 가격 체크 코퍼스의 정규화 규칙에 맞춘 판단이다. 의미상
  "욕실"로 보면 조건 간 순위가 달라진다
- 기존 스키마에서도 틀리던 분류(도기공사 섹션 → 철거, 철거공사 섹션의 폐기물처리비 → 철거)는 그대로 남아
  있다. 이번 테스트셋에선 가격 체크 범위가 넓어 리스크 결과에 영향이 없었지만(시뮬레이션으로 확인),
  경계 근처 견적서에선 가격 이상 판정을 바꿀 수 있어 별도 품질 이슈로 분리했다

## 프롬프트 캐싱

출력 스키마 축소로 비용을 줄인 뒤, 다음 레버로 **prompt caching**을 시도했다 — 정확도에 영향이
없는 개선이어야 한다는 원칙(latency 작업과 동일)에 따라 골랐다.

### 사전 확인 — 캐싱 대상 토큰 수

`count_tokens` API로 정적 프리픽스(툴 스키마 + `TOOL_USE_INSTRUCTIONS`)를 재보니 **2,150 토큰**
(툴 스키마만이면 1,287 토큰) — Sonnet 캐싱 최소 기준(1,024 토큰)을 넘어 캐싱이 걸린다.

### 1차 시도 — 지시문까지 캐싱 (순서 변경) → 되돌림

Anthropic 캐싱은 **요청 맨 앞부터 완전히 동일한 prefix**만 캐시 히트가 난다. 기존 메시지 순서가
`[이미지, 지시문]`이라 이미지가 매 청크 달라서 지시문까지는 캐싱이 안 걸렸다 — 순서를
`[지시문(cache_control), 이미지]`로 바꿔 지시문+툴 스키마 전체(2,150토큰)를 캐싱 대상으로 넣었다.

**정확도 재검증(순서만 변경, 캐싱 효과와 분리)**: 기존 벤치 테스트셋(S1~S3)으로 실제 API 재측정.

| 케이스 | 결과 |
|---|---|
| S1 (1청크) | ✅ 통과 |
| S2 (2청크) | ✅ 통과 |
| S3 (5청크) | ❌ 공과잡비·목공·창호·철거(1차)/도장(2차 재현 시) 금액이 허용범위(±5%) 밖 |

S3만 3회 더 반복해도(총 6회) 같은 공종들이 계속 허용범위를 벗어났다 — 우연한 변동이 아니라
**"지시문을 먼저 읽고 이미지를 나중에 보는" 순서 자체가 청크 수가 많은 표 추출 케이스에서 모델
출력에 실제 영향을 준다**는 뜻으로 판단, 이 방식은 되돌렸다.

### 2차 — 툴 스키마만 캐싱 (채택)

메시지 순서는 원래대로(`[이미지, 지시문]`) 유지하고, `tools` 항목에만 `cache_control`을 붙였다.
`tools`는 요청 구조상 메시지보다 항상 앞에 위치해서, 메시지 내용을 전혀 건드리지 않고도 캐싱이
걸린다 — 캐싱 대상은 1,287 토큰(지시문 제외)으로 줄지만, **메시지가 완전히 동일하므로 정확도
리스크가 0**이다. `RISK_ESTIMATE_TOOL`은 여러 곳에서 공유하는 모듈 전역 dict라 직접 수정하지 않고
호출부에서 `{**RISK_ESTIMATE_TOOL, "cache_control": ...}`로 얕은 복사해 붙였다.

- 단위 테스트: risk/collection 파라미터가 메시지는 완전히 동일하고 `tools`만 다른지, 캐싱이
  `RISK_ESTIMATE_TOOL` 원본을 변형하지 않는지 확인 (`tests/test_pipeline_vision_client.py`)

S4(8청크)는 이번 정확도 검증에서 제외했다 — 서로 다른 게시글 두 개를 합쳐 만든 인위적 최악
케이스라 실사용 분포를 대표한다고 보기 어렵고, latency 작업 때도 예산상 비용 측정에서 제외됐다.
실사용 청크 수 분포는 별도로 로그를 확인해야 안다.

### 2차 실측 — 캐싱이 실제로는 안 걸렸다

2차(툴 스키마만 캐싱) 코드로 실제 API 호출을 반복 측정했다.

- 1회차(10회 요청): 8/10이 Anthropic 쪽 `503 Overloaded`로 실패 — 우리 코드 문제 아님, 재시도
- 2회차: S1이 3/3 전부 동일하게 공과잡비/철거 금액이 크게 달라짐(650,000→1,200,000 /
  550,000→0). 처음엔 "캐싱이 출력에 영향을 준다"로 의심했으나, **`cache_creation_input_tokens`·
  `cache_read_input_tokens`가 전부 0** — 애초에 캐싱 자체가 한 번도 안 걸렸다. S1 결과 차이는
  캐싱과 무관한 별개 원인(추정: 이 경계 항목 자체의 실행 간 변동, `unit`/`quantity`를 뺀
  이후로 이미 몇 차례 관찰된 패턴)

원인 조사: `count_tokens` API로는 툴 스키마 단독이 1,287토큰으로 최소 기준(1,024)을 넘는데,
실제 요청에서는 캐시 생성조차 안 일어났다(`ANTHROPIC_LOG=debug`로 요청 바디에 `cache_control`이
정확히 포함된 것까지 확인, beta 헤더 추가도 효과 없음). 검색 결과, "cache_creation_input_tokens가
0이면 캐시 프리픽스가 최소 기준 미만인 것" — `count_tokens`가 보고하는 토큰 수와 실제 캐시 계산
방식에 차이가 있어, 1,287토큰(여유 260토큰)으로는 실제로 임계값을 못 넘는 것으로 보인다
([Anthropic 공식 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

### 3차 — system 파라미터로 지시문 이동 → 실패

캐시 순서는 `tools → system → messages`이고, breakpoint를 뒤 블록에 찍으면 그 앞 블록까지 한꺼번에
캐싱된다. `TOOL_USE_INSTRUCTIONS`를 유저 메시지가 아니라 `system` 파라미터로 옮기고 그 블록에
`cache_control`을 붙이면, `tools`(1,287) + `system`(지시문, ~860) 합쳐 다시 2,150토큰 수준으로
올라가 임계값을 여유 있게 넘는다. `messages`엔 이미지 하나만 남아 — 1차 시도(메시지 안에서 순서를
바꿔 S3 정확도가 깨졌던 것)와 달리 메시지 내용 자체는 안 건드린다.

실측 결과, 캐싱은 정상 작동했다(`cache_creation_input_tokens=1731` → 다음 호출
`cache_read_input_tokens=1731`, 실제 캐시 히트 확인). 하지만 정확도는 또 깨졌다:

| 케이스 | 실패 카테고리 |
|---|---|
| S1 (1청크) | 공과잡비, 설비, 욕실, 철거 |
| S2 (2청크) | ✅ 통과 |
| S3 (5청크) | 욕실, 철거 |

숫자를 뜯어보면 데이터 손실이 아니라 **순수 재분류**였다 — 설비 1,360,000원이 사라진 만큼
정확히 욕실 금액이 1,360,000원 늘었고, 철거 550,000원이 사라진 만큼 공과잡비가 정확히
550,000원 늘었다. `TOOL_USE_INSTRUCTIONS`의 위치가 "유저 메시지 → system"으로 바뀌면서,
지시문의 명시적 규칙("부대비용은 공과잡비로 분류")보다 이미지의 시각적 맥락(철거 섹션 아래
있음)에 더 끌려가는 것으로 추정된다 — 원래 설계(이미지 → 지시문 순서)에서는 지시문이 이미지
직후 마지막으로 읽히는 내용이라 규칙이 우선 적용됐는데, system으로 위치를 옮기며 이 인접성이
깨진 것으로 보인다.

### 4차 — few-shot 예시 추가 (system, 메시지는 원본 그대로) → 실패 

3차의 교훈을 반영해, `TOOL_USE_INSTRUCTIONS`는 원래대로 메시지에 남기고(순서 포함 완전히 동일),
`system`엔 **새 콘텐츠**(흔들리던 경계 규칙 2개를 구체 예시로 보여주는 few-shot 텍스트,
`RISK_CLASSIFICATION_EXAMPLES`)만 추가했다. 메시지를 전혀 안 건드리니 정확도 리스크가 없을
것으로 예상했다.

캐싱은 이번에도 정상 작동했다(1,240토큰 캐시 히트 확인). 그런데 정확도는 **여태까지 중 제일
심하게 깨졌다** — S1·S2·S3 전부 실패, 설비·욕실·철거·공과잡비가 모든 케이스에서 일관되게
틀어졌다(S2는 3차에서 통과했었는데 4차에선 실패로 바뀜). few-shot으로 문제되는 카테고리만
콕 짚어 예시를 준 게 오히려 모델을 그 예시 쪽으로 과도하게 끌어당긴(anchoring) 것으로 보인다.

## 결론 — 프롬프트 캐싱은 채택하지 않음

4가지 방식(메시지 순서 변경 / 툴 스키마만 캐싱 / 지시문을 system으로 이동 / system에 few-shot
추가)을 시도했고, 실제로 캐싱이 걸린 3건(1차, 3차, 4차) 전부 철거↔공과잡비·설비↔욕실 같은
**이미 알려진 경계 카테고리의 분류를 흔들었다** — 순서를 조금이라도 바꾸면 흔들리고, 아예 새
콘텐츠를 추가해도 흔들렸다(오히려 더 심하게). 이 모델+스키마 조합에서 명시적 분류 규칙이
"이미지 바로 다음"이라는 위치에 크게 의존하는 것으로 보이며, prompt caching이 요구하는 구조
(이미지 앞에 정적 콘텐츠를 두는 것) 자체가 이 의존성과 충돌한다.

Anthropic 공식 문서는 "20개 이상의 다양한 고품질 예시"를 캐싱과 함께 쓰는 패턴을 소개하는데,
이번에 쓴 예시(2개, 문제 카테고리만 좁게 타겟)보다 훨씬 큰 스케일이다. 이 방향을 계속 시도할 수는
있지만, 예시 세트를 제대로 만들고 검증하는 데만 상당한 시간이 들고(이번 코퍼스 40건 정답 채점
작업보다 큰 규모 추정), 지금까지 4전 4패인 걸 감안하면 성공 보장이 없어 **비용 대비 불확실성이
너무 크다고 판단, 여기서 중단한다.**

코드는 캐싱 이전 상태(PR #57, 스키마 축소만 적용)로 되돌렸다. 비용 절감은 스키마 축소로 얻은
18~29%가 최종 결과다. 다음 레버는 **이미지 해시 기반 결과 캐시**(API 호출 구조를 전혀 안 건드려
정확도 리스크가 0인 방식)로 넘어간다.
