# 리스크 진단 Vision 호출 병렬화 — 결과

## 배경

PM으로부터 "리스크 탐지 요청(`POST /risk-detector/analyze`)이 너무 오래 걸린다"는 문의가
들어왔다. 코드를 읽어보니 `RiskDetectorService._parse_images()`가 업로드된 이미지를 청크로
나눈 뒤, 청크마다 Vision API를 `await`로 하나씩 기다려서 호출하는 구조였다 — 응답시간이
청크 수에 비례해 선형으로 늘어날 수밖에 없는 구조다.

추측으로 고치지 않고 먼저 계측부터 했다: Vision 호출마다 소요시간·토큰 사용량을 로깅에
남기고(`risk_vision_call` 이벤트), 청크 수가 다른 케이스(1청크~8청크)로 베이스라인을 쟀다.

## 베이스라인 (개선 전, 실제 API 호출)

| 케이스 | 청크 수 | wall 시간 p50 |
|---|---:|---:|
| S1 | 1 | 32.8s |
| S2 | 2 | 97.3s |
| S3 | 5 | 196.4s |
| S4 | 8 | 264.5s |

파싱 소요시간이 Vision 호출 시간의 합과 거의 일치해, 모든 호출이 직렬로 실행되고 있음을
확인했다. 룰 기반 분석과 가격 이상 탐지(코퍼스 검색)는 합쳐서 0.2초 미만이라 병목이 아니었다.

## 변경 내용

- 모든 이미지·청크의 Vision 호출을 `asyncio.gather`로 동시에 실행. 완료 순서와 무관하게
  결과를 (이미지, 청크) 순서로 재조합해 기존 병합 로직(`merge_chunk_results`,
  `_merge_across_images`)은 그대로 유지
- 동기 클라이언트 + 스레드풀 대신 `AsyncAnthropic` 사용 — 동기 클라이언트를 그대로
  병렬화하면 호출 하나가 응답(수십 초)까지 스레드 하나를 붙잡아, 동시 요청 × 청크 수만큼
  기본 스레드풀을 금방 넘길 수 있었음
- 동시 호출 상한을 2단계로 분리
  - 프로세스 전체: `risk_vision_max_concurrency` (기본 20) — 서비스가 앱당 하나라 이
    세마포어가 곧 전역 상한. 요청 단위로만 제한하면 동시 요청 × 청크 수가 Anthropic
    조직 rate limit을 넘을 수 있음
  - 요청당: `risk_vision_max_concurrency_per_request` (기본 8) — 업로드 이미지 수에
    제한이 없어, 이게 없으면 이미지를 많이 올린 요청 하나가 전역 슬롯을 독점하고 그동안
    다른 사용자가 전부 대기하게 됨
- 청크 하나라도 실패하면 나머지 호출을 취소 — 어차피 버릴 결과에 API 비용을 쓰지 않도록
- 이미지 리사이즈·인코딩(CPU 바운드 작업)을 스레드풀로 이동 — 이벤트 루프 블로킹 제거

## 결과

**단건 응답시간 (실제 API, wall p50)**

| 케이스 | 청크 수 | 개선 전 | 개선 후 | 변화 |
|---|---:|---:|---:|---:|
| S1 | 1 | 32.8s | 33.2s | 변화 없음 (청크 1개라 병렬화 대상 없음) |
| S2 | 2 | 97.3s | 59.7s | −39% |
| S3 | 5 | 196.4s | 73.8s | **−62%** |
| S4 | 8 | 264.5s | 47.9s | **−82%** |

응답시간이 "청크 수 × 호출 시간"이 아니라 "가장 느린 호출 1건" 수준으로 떨어졌다 — 병렬화가
설계대로 동작한다는 직접적인 증거다.

**동시 부하 (k6, Vision API는 실측 지연 분포를 재현한 mock — 비용·rate limit 문제로 부하
자체는 mock으로 검증)**

| 동시 사용자 | p50 개선 전 | p50 개선 후 |
|---|---:|---:|
| 1명 | 185.5s | 57.6s |
| 5명 | 167.6s | 53.9s |

동시 10명 이상부터는 전역 동시 호출 상한(기본 20)이 처리량을 결정한다 — 슬롯 20개 ÷ 호출당
약 38초 기준으로 계산한 처리량과 실측치가 일치했다. 즉 그 이상은 코드가 아니라 상한값(설정)과
Anthropic 조직의 분당 요청/토큰 한도로 정해지는 용량 문제다.

비용(호출 수·토큰 사용량)은 이번 변경으로 바뀌지 않는다 — 병렬화는 오직 대기시간만 줄인다.

## 한계

- 부하 테스트는 실제 Anthropic API가 아니라 실측 지연 분포를 재현한 mock 기준이라, 동시
  호출이 급증할 때 실제로 발생할 수 있는 API 쪽 레이트리밋/지연 증가는 반영하지 못한다
- 같은 견적서를 병렬화 전/후로 반복 파싱해도 리스크 이슈 수가 실행마다 달라지는 현상을
  같이 발견했다 (모델 출력 자체의 실행 간 변동). 병렬화가 병합 결과를 바꾸지 않는다는 것은
  단위 테스트로 보장했지만, 이 변동성 자체는 응답시간과 별개의 품질 이슈라 이번 스코프에서
  다루지 않았다
- 동시 호출 상한(현재 20)은 예상 동시 사용자 수와 Anthropic 조직의 분당 한도를 확인해
  운영 트래픽에 맞춰 조정이 필요하다
