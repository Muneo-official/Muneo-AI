# 리스크 진단 이미지 파싱 캐시 — 설계와 원리

## 배경

이슈 #39(리스크 진단 응답 지연 + Vision API 비용)의 세 번째 작업이다. 응답시간은 병렬화로
([`risk_detector_latency_optimization.md`](risk_detector_latency_optimization.md)), 비용은 출력 스키마
축소로(PR #57, 요청당 −18~29%, [`risk_detector_cost_optimization.md`](risk_detector_cost_optimization.md))
줄였다. 프롬프트 캐싱은 네 가지 방식 모두 공종 분류 정확도를 깨뜨려 채택하지 않았다(같은 문서 후반부).

남은 안전한 수단이 "같은 이미지를 다시 올리면 API를 다시 부르지 않는 것"이다. 요청 구조(프롬프트·스키마·
메시지 순서)를 전혀 건드리지 않으므로 정확도 위험이 없다.

목적은 두 가지다.

1. **비용·응답시간** — 캐시가 걸린 이미지는 Vision 호출 0회.
2. **결과 일관성** — 모델 출력은 실행마다 조금씩 달라서, 같은 견적서를 다시 올리면 철거↔공과잡비처럼
   경계에 있는 항목의 분류가 바뀔 수 있었다. 캐시가 있으면 같은 이미지는 항상 같은 결과를 받는다.

재업로드가 실제로 얼마나 일어나는지는 모른다(기존 로그·`risk_reports`에 이미지 식별 정보가 없었다).
그래서 효과는 추정하지 않고, 로그로 사후 측정하도록 만들었다(아래 "효과 측정").

## 전체 흐름

```
업로드된 이미지들
   │
   ▼
① 이미지마다 지문(sha256) 계산
   │
   ▼
② 지문 + 파싱 버전으로 Mongo(risk_parse_cache) 조회
   │
   ├─ 히트 → 저장된 line_items 그대로 사용 (Vision 호출 없음)
   └─ 미스 → 청크 분할 → Vision 호출 → 청크 병합 → 저장
   │
   ▼
③ 업로드 순서대로 이미지 간 중복 제거하며 합침
   │
   ▼
④ 룰 분석 + 고층 양중비 + 가격 이상 탐지 + 리포트 조립   ← 캐시와 무관하게 매번 실행
```

캐시가 끼어드는 곳은 ②뿐이고, 나머지는 기존 코드 그대로다. 구현은
`app/domain/risk_detector_service.py`의 `_parse_images()`, 저장소는
`app/repositories/risk_parse_cache_repository.py`.

## 설계 결정

### 이미지 지문 — 원본 바이트의 sha256

바이트가 1비트라도 다르면 완전히 다른 값이 나오고, 같으면 항상 같은 값이 나온다. 서로 다른 이미지가
같은 값을 가질 확률은 현실적으로 0이다. 그래서 이미지 자체 대신 64자리 문자열만 비교한다. **이미지
원본은 저장하지 않는다.**

리사이즈 전 원본 바이트로 계산하므로 "완전히 같은 파일"에만 걸린다. 같은 견적서라도 다시 캡처하거나
재압축하면 다른 이미지로 취급된다.

### 캐시 키에 파싱 버전을 붙인다

키는 `sha256:RISK_PARSE_VERSION`이다. 같은 이미지라도 파싱 방식이 바뀌면 결과가 달라진다(PR #57에서
스키마를 조금 바꿨을 때 경계 공종이 재분류된 것처럼). 그래서 결과에 영향을 주는 것들을 해시해 버전으로
쓴다(`pipeline/vision_client.py`).

- 모델(`claude-sonnet-4-6`), `max_tokens`
- 리스크 전용 출력 스키마(`RISK_ESTIMATE_TOOL`)
- 지시문(`TOOL_USE_INSTRUCTIONS`)
- 청크 분할 설정(최대 너비, 분할 임계값, 청크 높이, 겹침)

이 중 하나라도 바꾸면 키가 달라져 예전 캐시와 절대 일치하지 않으므로, 수동으로 지우지 않아도 자동으로
새로 파싱된다. **스키마·프롬프트 변경 = 일관성 리셋**이다(의도된 동작).

병합 로직(`pipeline.parsing.merge_chunk_results`)은 코드라 해시로 잡을 수 없다. 결과가 달라지게 고치면
`_PARSE_LOGIC_REVISION`을 올린다.

### 최종 리포트가 아니라 파싱 결과만 저장한다

리스크 진단은 두 단계다.

| 단계 | 하는 일 | 비용 | 실행 간 결과 |
|---|---|---|---|
| 파싱 | 이미지 → 항목 목록 (Claude) | 비용·시간 거의 전부 | 조금씩 다름 |
| 판정 | 항목에 룰·통계 적용 (우리 코드) | 0 | 입력이 같으면 항상 같음 |

판정 단계는 이미지 외에 층수·지역·평수 같은 폼 입력도 쓴다. 최종 리포트를 통째로 저장하면 "2층으로
분석한 리포트"를 15층 요청에 돌려주게 된다. 파싱 결과만 저장하면 두 목적이 동시에 풀린다 — 비용은
파싱을 건너뛰어서, 일관성은 실행마다 흔들리던 유일한 단계가 고정돼서.

### 요청 단위가 아니라 이미지 단위

```
1회차: [A, B, C]  → 전부 미스 → 3장 파싱, 3장 저장
2회차: [A, B, D]  → A·B 히트, D만 파싱
```

겹치는 페이지는 재사용되고, 합칠 때는 원래 업로드 순서를 따른다. 한 요청 안에 같은 이미지가 여러 장이면
한 번만 파싱한다.

### 저장소 — MongoDB `risk_parse_cache`

이미 motor로 연결돼 있고 워커·재배포 간에 공유된다. 파일·인메모리는 재배포나 재시작 때 사라진다.

```json
{ "_id": "<sha256>:<version>", "line_items": [...],
  "input_tokens": 3384, "output_tokens": 2479,
  "created_at": ISODate, "last_used_at": ISODate }
```

토큰 수는 처음 파싱할 때 든 비용이다. 히트 때 꺼내 "아낀 토큰"으로 로그에 남긴다.

## 일관성 장치

1. **처음 저장된 결과를 덮어쓰지 않는다(`$setOnInsert`).** 같은 이미지가 거의 동시에 두 번 올라오면 둘 다
   미스라서 각자 파싱하고 결과가 다를 수 있다. 나중 것이 덮어쓰면 "아까랑 결과가 다른" 상황이 생기므로,
   문서가 없을 때만 넣는다. 먼저 저장된 결과가 기준이 된다.
2. **슬라이딩 TTL 90일.** `created_at`에 TTL을 걸면 매일 쓰이는 이미지도 90일째에 지워져 재파싱되고 결과가
   바뀔 수 있다. 그래서 히트할 때마다 `last_used_at`을 갱신하고 TTL은 이 필드에 건다. 계속 쓰이는 이미지는
   만료되지 않고, 90일 동안 아무도 안 올린 이미지만 정리된다(`scripts/setup_indexes.py`).
3. **빈 결과는 저장하지 않는다.** 일시적인 파싱 실패가 "추출 실패"로 굳지 않도록. 다음 업로드 때 다시 시도한다.

## 안전장치

- **캐시 장애 시 폴백.** Mongo 조회·저장이 실패하면 로그(`risk_parse_cache_error`)만 남기고 캐시 없이 Vision을
  호출한다. 캐시 때문에 분석이 실패하지 않는다.
- **Vision 호출이 하나라도 실패하면 아무것도 저장하지 않는다.** 일부 청크만 성공한 불완전한 결과가 남지 않게.
- **끄는 스위치.** `RISK_PARSE_CACHE_ENABLED=false`(기본 켜짐).
- **벤치 서버는 기본으로 꺼짐.** 벤치는 같은 이미지를 반복해 모델 변동 폭을 재는 도구라, 캐시가 켜져 있으면
  2회차부터 Vision을 안 불러 측정이 무의미해진다. `--parse-cache`로만 켜고, mock 모드(가짜 결과가 실제 캐시에
  저장됨)나 `--risk-schema full`(버전 키에 반영 안 됨)과는 같이 쓸 수 없다.

## 응답시간 오버헤드

캐시가 추가하는 작업과 비용(캐시 미스, 즉 기존과 같은 경로 기준):

| 작업 | 시간 | 비고 |
|---|---|---|
| sha256 계산 | 5MB 약 2ms, 20MB 약 9ms | 로컬 실측 |
| Mongo 조회 1회 | 수십 ms (Atlas 왕복 1회) | 이미지 수와 무관하게 한 번에 조회 |
| Mongo 저장 | 왕복 1회 | 여러 장이어도 동시에 보냄 |

기존 응답시간이 S3 약 74초, S4 약 48초이므로 추가분은 0.5% 미만이다. 캐시가 걸리면 Vision 호출(수십 초)이
통째로 빠져 응답이 수 초 이내로 줄어든다(실측 전).

단, Mongo가 아예 응답하지 않는 장애 상황에서는 조회가 `serverSelectionTimeoutMS`(5초)만큼 기다린 뒤 폴백한다.
이 경우 가격 이상 탐지(코퍼스 검색)도 같은 Mongo를 쓰므로 캐시와 무관하게 이미 느려지거나 실패하는 상황이다.

## 효과 측정

`risk_analyze_timing` 로그에 요청마다 남긴다.

| 필드 | 의미 |
|---|---|
| `image_sha256` | 이미지별 지문 (캐시를 꺼도 남김) |
| `parse_cache_hits` / `parse_cache_misses` | 캐시에서 꺼낸 / 새로 파싱한 이미지 수 |
| `parse_cache_saved_input_tokens` / `parse_cache_saved_output_tokens` | 히트로 아낀 토큰 |

처음 올린 이미지는 반드시 미스, 다시 올린 이미지는 반드시 히트이므로 **히트율이 곧 재업로드 비율**이다.
아낀 토큰에 단가(입력 $3 / 출력 $15 per 1M)를 곱하면 절감액이 된다. `chunk_count`·`input_tokens`는 실제
Vision 호출분만 센다.

## 실측 (2026-09-30, 실제 API, S1 = 이미지 1장·1청크)

같은 코드에서 캐시만 끄고/켜서 쟀다. 캐시를 끈 경로는 dev와 해시 계산(ms 미만)만 다르다.

- A. 캐시 없음: `bench.server` 기본(캐시 꺼짐), S1 × 3회 → `logs/bench/latency_no-cache_20260930_135635.json`
- B. 캐시 있음: `bench.server --parse-cache`, 빈 캐시에서 S1 × 6회(1회 미스 + 5회 히트) → `logs/bench/latency_image-cache_20260930_135835.json`

| | n | wall p50 | 요청당 비용 | 입력/출력 토큰 |
|---|---:|---:|---:|---:|
| A. 캐시 없음 | 3 | 24.0s | $0.0336 | 3,497 / 1,541 |
| B. 미스(첫 업로드) | 1 | 23.6s | $0.0336 | 3,497 / 1,540 |
| B. 히트(재업로드) | 5 | **0.07s** | **$0** | 0 / 0 |

**캐시 오버헤드 (서버 로그 직접 측정)**
- 미스: 조회 5.5ms + 저장 13.3ms = **약 19ms** — 응답시간 23.6s의 0.08%. 전체 wall 비교로는 Vision 변동(23.6~25.1s)에
  묻혀 보이지 않는 크기라 따로 쟀다.
- 히트: 조회 18~21ms(찾기 + `last_used_at` 갱신, Mongo 왕복 2회). 히트 요청 전체가 0.07~0.13s.

**재업로드 한 번당 절감:** 응답 24.0s → 0.07s(−99.7%), 비용 $0.0336 → $0(입력 3,497·출력 1,540 토큰, 로그의
`parse_cache_saved_*`에 그대로 찍힘). 큰 견적서일수록 절감 폭이 커진다(S3는 요청당 약 $0.21, 약 63s).

**정확도·일관성**
- A 3회, B 6회 모두 항목 28개·금액 합계 7,386,000원·공종별 금액·리스크 이슈 4건이 완전히 같다. S1 정답(28행,
  7,386,000원, `risk_detector_cost_optimization.md`)과도 일치한다.
- 다만 S1은 캐시가 없어도 결과가 흔들리지 않았다(1청크짜리 쉬운 케이스). 일관성 효과는 아래 S3로 따로 쟀다.

## 실측 — 일관성 (2026-09-30, S3 = 이미지 2장·5청크)

S3는 캐시 없이 돌린 과거 기록 12개가 전부 실행마다 달랐던 케이스다. 같은 방식으로 캐시만 끄고/켜서 쟀다.

- A. 캐시 없음, S3 × 3회 → `logs/bench/latency_consistency-no-cache_20260930_140725.json`
- B. 캐시 있음(빈 캐시), S3 × 4회(1회 미스 + 3회 히트) → `logs/bench/latency_consistency-cache_20260930_141012.json`

| | 항목 수 | 금액 합계 | 리스크 이슈 (누락) | 서로 다른 결과 |
|---|---|---|---|---:|
| A. 캐시 없음 (3회) | 163 / 168 / 165 | 84,241,483 / 87,571,483 / 84,831,483 | 12 / 12 / **13** (2 / 2 / **3**) | **3가지** |
| B. 캐시 있음 (4회) | 163 × 4 | 84,241,483 × 4 | 12 × 4 (2 × 4) | **1가지** |

캐시가 없을 때 같은 이미지를 3번 올리면:
- 금액 합계가 최대 **333만 원** 차이 났다.
- 공종별 금액이 크게 움직였다 — 가구 1,376만~1,726만 원, 욕실 448만~654만 원, 목공 570만~763만 원, 설비 341만~489만 원.
  경계 공종(가구↔목공, 설비↔욕실)의 분류가 실행마다 바뀐 것이다.
- **리스크 판정 자체가 바뀌었다.** 3회차에만 "누락" 이슈가 하나 더 나왔다. 사용자 입장에선 같은 견적서를 다시
  올렸더니 "빠진 공종"이 생겼다 없어지는 셈이다.

캐시가 있으면 4회 모두 항목·금액·공종별 금액·이슈가 완전히 같았다. 첫 파싱 결과가 기준이 되고, 이후 재업로드는
그 결과를 그대로 받는다.

같은 항목 수·합계라도 공종 분배가 다를 수 있다는 것도 보였다. A 1회차와 B 미스는 둘 다 163개·84,241,483원인데
가구·목공 금액이 90만 원씩 반대로 옮겨가 있다. 합계만 비교하면 이런 차이는 보이지 않는다.

**캐시가 고정하는 건 "첫 파싱 결과"다.** 그 결과가 정답이라는 보장은 없다 — 캐시는 정확도를 올리지 않고,
흔들림을 없앨 뿐이다. 정확도는 스키마·프롬프트(PR #57)의 몫이다.

**S3 비용·시간:** 미스 62.9s·$0.207, 히트 0.07s·$0(입력 16,204·출력 10,556 토큰 절감). 미스 오버헤드는 조회 5.6ms +

- 재업로드 비율(= 운영 히트율)은 아직 모른다. 절감 총액은 운영 로그의 `parse_cache_hits` 비율로 사후 산출한다.
- 바이트가 완전히 같을 때만 걸린다. 같은 견적서를 다시 캡처·재압축하면 미스다.
- 표본이 작다(S1 히트 5회, S3 캐시 없음 3회·히트 3회). 히트 시간은 S1·S3 모두 0.07s 안팎으로 케이스 크기와 무관했다.
- 캐시는 첫 파싱 결과를 고정할 뿐, 그 결과가 틀렸으면 틀린 채로 고정된다. 파싱 방식을 고치면(버전 변경) 전부 새로 파싱된다.
