# 검색 품질 평가 — 요약

전체 조사 과정과 원본 로그: [`reranker_hybrid_eval.md`](./reranker_hybrid_eval.md)
(시간순 작업 기록 — 아래는 그중 최종 결론만 정리한 것)

## Stage 필터란?

검색 전에 "조건에 안 맞는 사례는 후보에서 아예 제외"하는 단계적 필터. 예를 들어
"30평, 서울, 도배+타일" 요청이 들어오면, 전체 코퍼스를 텍스트 유사도로만 뒤지는 게
아니라 Mongo에 "평수 30±7, 지역=서울, has_도배=true, has_타일=true인 문서만" 조건을
걸고 그 안에서 벡터 검색을 한다. 조건을 다 걸면 결과가 너무 적을 수 있어(3건 미만)
단계적으로 완화하며 재시도한다.

| Stage | 조건 |
|---|---|
| 1 | 평수 + 지역 + 공종 + 자재등급 (전체) |
| 2 | 자재등급 제외 |
| 3 | 지역도 제외 |
| 4 | 평수도 제외 (공종만) |
| 5 | 조건 없음 (최후 수단) |

각 단계에서 결과가 3건 이상이면 그 단계에서 멈춘다. 실측 결과 24개 쿼리 중 22개가
Stage 2, 2개가 Stage 1에서 멈췄고 Stage 3~5로 밀린 경우는 0건 — 정밀 필터가 거의
항상 성공한다는 뜻이며, 이게 정확도를 82.5%까지 끌어올린 핵심 원인이다.

## 문제

1. **코퍼스 오염(81%)**: 크롤러의 페이지 전환 race condition으로, 게시글 693/855건이
   "제목은 A 게시글인데 실제 저장된 내용은 B 게시글"인 상태로 섞여 있었다. 이 중 89%는
   이번 조사 이전부터 있던 근본 버그였다(신규로 생긴 문제가 아님).
2. **평가 방법론 자체의 결함**: 그동안 써온 `eval/retrieval_eval.py`는 실제 서비스가
   쓰는 평수·지역·공종 기반 필터링(Stage 1~5 점진적 완화)을 전혀 테스트하지 않고,
   필터 없는 벡터 검색만으로 후보를 뽑아 측정하고 있었다.

## 조치

1. 오염 감지 스크립트(`scripts/audit_content_mismatch.py`) 작성 → 693건 식별 →
   삭제 → `post_url`부터 재크롤링·재파싱
2. 임베딩 파이프라인 정합성 확보(빈 요청글 대체 텍스트, "py" 표기 평수 추출, embedding
   백필 자동화 — `scripts/backfill_new_embeddings.py`)
3. 실제 production 경로(Stage 필터 포함)를 그대로 재현하는 평가 도구 신설
   (`eval/production_retrieval_eval.py`)

## 결과 — precision@15, 24개 테스트 쿼리, 정리된 코퍼스 기준 (전량 라벨 커버리지)

| 단계 | precision@15 | 비고 |
|---|---:|---|
| 벡터 검색 단독 (필터 없음) | 17.2% | 순수 텍스트 유사도만 — `eval.retrieval_eval` |
| + 하이브리드(BM25+RRF) + 크로스인코더 리랭킹 (필터 없음) | 20.6% (+3.4%p) | `eval.retrieval_eval` |
| + Stage 필터(평수·지역·공종), 벡터 단독 | 78.0% (+57.4%p) | `eval.production_rerank_ablation_eval` |
| + Stage 필터 + 하이브리드+리랭킹 (SIZE_RANGE=±7평) | 82.5% (+4.5%p) | `eval.production_retrieval_eval` |
| **+ 동일 + 평수 필터 ±7→±5평 (실제 production 경로, 최종)** | **93.2%** (+10.7%p) | `eval.production_retrieval_eval` |

- Stage 필터 채택 현황(24개 쿼리): Stage 1(전체 조건) 2건, Stage 2(등급만 완화) 21건,
  Stage 3(지역 완화) 1건, Stage 4~5 0건 — 구조적 필터가 거의 항상 성공한다.
- 리랭킹의 순효과(같은 후보 풀 안에서 재정렬만 했을 때)는 필터 없을 때 +3.4%p, 필터
  있을 때 +4.5%p — 필터 유무와 무관하게 꾸준히 긍정적이지만 개선폭의 대부분은 필터가
  차지한다. 24개 쿼리 중 7개는 후보 자체가 15개 이하라 재정렬이 결과에 영향을 주지
  않았다(그 경우도 위 평균에 포함됨).

## 추가 개선: 실패 쿼리 분석 → 평수 필터 튜닝

가장 정밀도 낮은 3개 쿼리의 실제 후보를 까본 결과, 라벨된 후보 전체를 "쿼리-사례
평수차이"로 묶었을 때 relevant 비율이 7평 지점에서 65.5%→22.2%로 절벽처럼 떨어지는
걸 확인했다. 원인은 production 필터(`SIZE_RANGE=±7평`)와 사람이 매긴 라벨 기준
(`±5평`)이 애초에 어긋나 있던 것 — 필터를 라벨 기준에 맞춰 ±5평으로 좁히자
82.5%→93.2%(+10.7%p)로 뛰었고, 신규로 후보권에 들어온 39건을 라벨링해 전량 커버리지를
유지한 채 검증했다. Stage 채택 분포는 거의 그대로였고(24개 쿼리 중 지역 조건까지
완화된 건 1개뿐), 유일하게 정밀도가 낮았던 쿼리가 정확히 그 케이스였다 — "지역
조건이 빠지면 정밀도가 떨어진다"는 기존 결론과 부합한다.

같이 검토했던 "지방(15개 시/도 통합) 버킷을 세분화" 아이디어는 사용자 입력 스키마가
`Literal["서울","수도권","지방"]`로 고정돼 있어 — 즉 쿼리 자체에 "부산" 같은 세부
지역 정보가 없어 — 검색 로직만으로는 구현 불가능하다는 걸 확인하고 기각했다(입력
스키마 변경이 필요한 별개 과제).

## 추가 발견: 비주거 사례 오염 + 평당 단가 stale 버그

Swagger로 실제 응답을 검증하다가 두 가지를 더 찾았다.

1. **비주거 사례 오염**: 화재 피해 상가주택 복구 공사(평당 396만원, 다른 사례 대비
   2~4배)가 "아파트 리모델링" 검색 결과에 섞여 들어가 있었다 — DB에 공간유형 필드가
   없어 걸러낼 방법이 없었던 것. 코퍼스 709건 중 "상가/공장/근생/점포" 9건을 확인해
   `is_non_residential` 플래그를 세우고 검색에서 항상 제외했다.
2. **평당 단가 stale 버그**: `참고_사례`의 평당이 ingest 시점에 저장된 필드를 그대로
   읽어와서, size_pyeong이 나중에 보정된 116건(16%)은 총금액·평수는 정상인데 평당만
   0으로 남아 있었다. 매번 `total_cost/size_pyeong`으로 라이브 계산하도록 고쳤다.

precision@15는 93.2%→93.1%로 사실상 그대로(오염 사례가 전체의 1.3%라 샘플 영향이
작음) — 하지만 후보 풀이 작은 쿼리일수록 극단치 하나가 최댓값을 크게 왜곡할 수 있어
구조적으로 막아둔 데 의미가 있다.

## 결론

**핵심 지렛대는 구조적 필터링**(지역/평수/공종을 벡터 검색 전에 미리 좁히는 것)이다 —
필터 하나만으로 17.2%→78.0%(+57.4%p)가 뛴다. 하이브리드 리랭킹은 필터 위에 얹어도
꾸준히 +4.5%p를 추가로 벌어주고, 실패 쿼리 분석으로 찾아낸 평수 필터 관용치
불일치(±7→±5)를 고치자 추가로 +10.7%p가 붙었다. 최종 93.2%가 지금 시점 실사용
기준으로 신뢰할 수 있는 수치다.

## 재현

```bash
python -m scripts.audit_content_mismatch          # 코퍼스 오염 감사
python -m scripts.backfill_new_embeddings          # embedding 백필
python -m eval.refresh_pool && python -m eval.flag_review_rows   # (필터 없음) pool 갱신
python -m eval.retrieval_eval                       # 필터 없음 벡터 vs 하이브리드

python -m eval.label_production_candidates          # production 경로(필터+리랭킹) 신규 후보 추출
python -m eval.apply_production_labels
python -m eval.production_retrieval_eval            # 필터+리랭킹 최종 수치

python -m eval.label_rerank_ablation_candidates     # 필터+벡터단독 쪽 신규 후보 추출
python -m eval.apply_production_labels --review-file eval/test_inputs/rerank_ablation_review.csv
python -m eval.production_rerank_ablation_eval      # 필터만 vs 필터+리랭킹 비교
```
