# 리랭커 + BM25 하이브리드 검색 평가 기록

실행일: 2026-08-30

## 무엇을 테스트했나

`EstimateEngine.retrieve_cases()`가 반환하는 **벡터 검색 단독 순위**와,
`EstimateEngine._hybrid_rerank()`가 같은 후보 집합에 **BM25+RRF 결합 → Cross-encoder
(`Dongjin-kr/ko-reranker`) 재정렬**을 적용한 순위를 같은 ground truth 라벨로 채점해 비교했다.

주의: 이 스크립트는 리랭커와 BM25+RRF를 분리해서 각각의 단독 효과를 측정하지 않는다.
`_hybrid_rerank()` 자체가 프로덕션에서 두 단계를 항상 붙여서 쓰기 때문에, 여기서 측정한 건
**"BM25+RRF+cross-encoder를 합친 하이브리드 파이프라인 전체"가 벡터 단독 대비 내는 효과**다.
두 기법을 따로 떼서 보려면 `_hybrid_rerank()`를 단계별로 쪼개 호출하는 별도 스크립트가 필요한데,
지금은 범위 밖으로 남겨둔다.

## 평가 방법

- Ground truth: `eval/test_inputs/pool.json` — 24개 쿼리, 쿼리당 벡터 top-20 + BM25 top-20을 합친
  pool(TREC 스타일 pooling)에 사람이 관련성(0/1)을 라벨링한 것 (`docs/IMPLEMENTATION_LOG.md` 2-7
  참고 — 915건 중 187건 사람 검토, 47건 수정).
- 후보 범위: 쿼리별 벡터 검색 top-20만 사용. `_hybrid_rerank()`가 실제로도 그 순간 벡터 후보 집합
  안에서만 BM25를 계산하므로, 이 평가는 production 동작을 그대로 재현한 것 — 벡터 후보 밖 문서는
  하이브리드도 원천적으로 못 찾아오므로 recall이 100%를 못 채우는 게 정상.
- 지표: precision@k(주 지표), pool 내 recall@k(보조 지표, 전체 코퍼스 기준 recall 아님).

## 결과

쿼리 수: 24

| 지표 | 벡터 단독 | 하이브리드+리랭킹 | 변화 |
|---|---:|---:|---:|
| precision@5 | 33.3% | 30.0% | **-3.3%p** |
| recall@5 | 14.9% | 12.2% | -2.7%p |
| precision@10 | 27.1% | 30.0% | **+2.9%p** |
| recall@10 | 22.5% | 24.3% | +1.8%p |

## 해석

혼재된 결과다 — 무조건 개선이라고 포장하지 않는다.

- **top-5**: 하이브리드+리랭킹이 오히려 약간 나쁘다 (precision -3.3%p, recall -2.7%p).
- **top-10**: 하이브리드+리랭킹이 약간 낫다 (precision +2.9%p, recall +1.8%p).
- 24개 쿼리는 통계적으로 작은 표본이라 이 몇 %p 차이가 노이즈일 가능성을 배제할 수 없다 —
  "리랭킹이 top-5는 못 살리고 top-10은 살린다"고 확정할 근거는 아니다.
- 가능한 설명: cross-encoder가 겨냥하는 "복합 조건 매칭" 효과는 이미 벡터 유사도가 충분히 정확한
  좁은 top-5 범위에서는 개입 여지가 적어 오히려 순서를 흔들 수 있는 반면, top-10처럼 조금 더 넓은
  범위에서는 벡터가 놓친 사례를 리랭킹이 건져오는 효과가 나타나는 것으로 보인다.

비용 대비 효과 관점에서도 짚어둘 것: 하이브리드+리랭킹 파이프라인은 추론 시간이 벡터 단독 대비
유의미하게 늘어난다(`docs/IMPLEMENTATION_LOG.md` 기준 요청당 약 6초). 지금 결과만으로는 이 비용을
정당화할 만큼 확실한 개선이라고 말하기 어렵고, 추가 검증(쿼리 표본 확대, top-5/top-10 분리 원인 조사)이
필요하다.

## 원인 분석 — 왜 top-5/top-10에서 반대 방향으로 움직였나

순위 이동을 직접 추적해보니(리랭킹 전/후 top-5·top-10에 들고 나는 관련 사례를 개별 확인), 쿼리마다
우연히 흔들린 게 아니라 **특정 article_id가 여러 쿼리에서 반복적으로 top-5 밖으로 밀려나거나
끌어올려지는 패턴**이 있었다.

| | 반복적으로 밀려난 사례 | 반복적으로 끌어올려진 사례 |
|---|---|---|
| article_id | 879345, 882159, 882169, 883238, 884553 | 886848, 880249, 881163, 879360 |
| 등장한 쿼리 수 | 각 4~5개 쿼리 | 각 2~4개 쿼리 |
| `request_body_text` 길이 | 166~270자 (평균 **212자**) | 431~752자 (평균 **560자**, 약 2.6배) |

**가설**: `_hybrid_rerank()`가 쓰는 BM25 토크나이저(`_tokenize()`, `app/domain/estimate_engine.py:38-42`)는
정규식 `[\w가-힣]+`로 텍스트를 자른다 — 코드 주석엔 "음절 단위"라고 적혀 있지만 실제로는 **공백 기준
어절 단위** 토큰화다(형태소 분석 없음, 조사 미분리). 요청글을 길게 쓴 사례일수록 서로 다른 어절이
많아져서 쿼리 텍스트와 우연히 겹치는 어절이 늘어나고, 이게 실제 관련성과 무관하게 BM25 점수를
끌어올린다는 가설.

**1차 검증(간단한 수정 시도) — BM25 `b`(길이 정규화 강도) 조정**: `rank_bm25.BM25Okapi`의 기본값
`b=0.75`(부분 정규화)를 `b=1.0`(완전 정규화)으로 올려 같은 24개 쿼리로 재평가.

| BM25 `b` | precision@5 | recall@5 | precision@10 | recall@10 |
|---|---:|---:|---:|---:|
| 0.75 (기본) | 30.0% | 12.2% | 30.0% | 24.3% |
| 1.0 (완전 정규화) | 30.0% | 12.2% | 30.0% | 24.3% |

**결과: 완전히 동일 — `b` 조정으로는 해결되지 않는다.**

**해석(1차, 이후 아래 "정정"에서 뒤집힘)**: BM25의 `b` 파라미터는 "같은 단어의 반복 등장"에 대한
길이 보정만 한다. 지금 관찰된 편향은 반복이 아니라 서로 다른 어절의 절대 개수 차이에서 온다고
봤다 — 하지만 아래 "정정" 절에서 밝히듯, 애초에 **이 eval 구조에서는 BM25가 최종 순위에 아무
영향도 못 준다**(`RERANK_POOL=20`이 후보 풀 크기와 같아서 걸러지는 게 없음). 그래서 `b=0.75`든
`b=1.0`이든 결과가 똑같았던 진짜 이유는 "길이 정규화가 편향을 못 없애서"가 아니라 **BM25 자체가
처음부터 결과에 영향을 준 적이 없었기 때문**이다 — 이 실험 하나만으로는 두 설명을 구분할 수 없었고,
아래 `vector_ce_only_experiment.py`로 BM25를 통째로 제거해보고 나서야 후자가 맞다는 게 드러났다.

## 정정 — 위 "BM25 원인" 분석은 이 eval 범위 안에서는 틀렸다

`eval/vector_ce_only_experiment.py`로 **BM25/RRF 단계를 완전히 제거**하고 "벡터 top-20 →
cross-encoder만" 재정렬해서 재평가했다.

| 지표 | 벡터 단독 | 벡터+CE(BM25 제외) | 변화 |
|---|---:|---:|---:|
| precision@5 | 33.3% | 30.0% | -3.3%p |
| recall@5 | 14.9% | 12.2% | -2.7%p |
| precision@10 | 27.1% | 30.0% | +2.9%p |
| recall@10 | 22.5% | 24.3% | +1.8%p |

**하이브리드(BM25+RRF+CE) 결과와 소수점까지 완전히 동일하다.** 즉 BM25는 최종 순위에 아무 영향도
주지 못했다 — 원인은 코드 구조에 있다:

```python
# app/domain/estimate_engine.py:610-611
rrf_scores = self._reciprocal_rank_fusion([vector_rank_ids, bm25_rank_ids])
pool_ids = sorted(rrf_scores, key=rrf_scores.get, reverse=True)[:min(len(ids), RERANK_POOL)]
```

`RERANK_POOL = 20`(`estimate_engine.py:29`)이고, 이 eval의 후보 풀도 `build_pool.py`와 맞추려고
벡터 top-20으로 뽑았다. `min(20, 20) = 20`이라 **BM25/RRF가 순서를 아무리 바꿔도 아무도 걸러지지
않고 20개 전부 cross-encoder로 넘어간다.** Cross-encoder는 (쿼리, 문서) 쌍을 독립적으로 채점하므로
입력 순서는 최종 결과에 영향을 줄 수 없다 — 즉 이 eval 설계 안에서는 **BM25가 최종 순위에 기여할
수학적 여지 자체가 없었다.**

**따라서 앞서 "요청글 길이 때문에 BM25가 편향된다"는 분석은 원인 지목이 틀렸다** — 실제로 순위를
흔든 건 BM25가 아니라 **cross-encoder 자체**다. 반복적으로 밀려난/끌어올려진 사례의 텍스트 길이
차이(평균 212자 vs 560자)라는 관찰 자체는 유효하지만, 그 편향의 발생 지점은 BM25가 아니라
cross-encoder(`Dongjin-kr/ko-reranker`)가 더 상세한 텍스트를 더 관련 있다고 채점하는 경향일
가능성이 높다 — 아직 직접 검증은 안 했다.

**이 eval 설계 자체의 한계**: 프로덕션(`EstimateEngine.__init__`의 `vector_candidate_pool=40`)은
벡터 후보를 40개 가져온 뒤 RRF로 20개까지 추리므로 BM25가 실제로 필터링 역할을 한다. 하지만 이
평가의 ground truth(`pool.json`)는 애초에 벡터 top-20만 담고 있어서, BM25가 걸러낼 대상 자체가
없다 — **BM25의 진짜 기여도는 이 eval로는 검증되지 않은 상태로 남아있다.** 제대로 보려면 pool을
벡터 top-40 기준으로 다시 만들어야 한다(재라벨링 비용 발생).

**남은 선택지(미착수, 다음에 검토)**:
- ~~cross-encoder가 텍스트 길이/상세도에 실제로 편향되는지 직접 검증~~ → 아래 "확정" 절에서 완료,
  인과관계로 확인됨
- BM25의 진짜 기여도를 보려면 pool을 벡터 top-40 기준으로 재구축(재라벨링 필요) — 비용이 커서
  우선순위는 낮음
- 형태소 분석기(예: `kiwipiepy`, `mecab`) 도입은 이번 정정으로 근거가 약해짐 — BM25가 최종
  순위에 영향이 없었다면 BM25 토크나이저를 개선해도 지금 관찰된 문제는 안 고쳐짐(보류)

## 확정 — cross-encoder 길이 편향, 통제 실험으로 인과관계 확인

`eval/ce_length_bias_experiment.py`: 반복적으로 밀려난 5개 사례 각각의 원문 뒤에 **견적과 완전히
무관한 필러 문장**("빠른 답변 부탁드립니다, 감사합니다" 류의 상투적 인사말 — 평수/지역/공종 등
매칭에 쓰일 정보는 전혀 없음)을 이어붙여 길이만 인위적으로 560자(끌어올려진 사례들의 평균 길이)로
맞춘 뒤, 원본과 패딩 버전 각각에 대해 같은 쿼리로 cross-encoder 점수를 직접 비교했다.

| article_id | 원본 길이 | 원본 점수 | 패딩 후 길이 | 패딩 후 점수 | 변화 |
|---|---:|---:|---:|---:|---:|
| 879345 | 303 | 0.0438 | 560 | 0.1245 | **+0.0807** |
| 882159 | 234 | 0.1466 | 560 | 0.3432 | **+0.1966** |
| 882169 | 205 | 0.0395 | 560 | 0.1265 | **+0.0870** |
| 883238 | 199 | 0.0067 | 560 | 0.0124 | +0.0056 |
| 884553 | 282 | 0.0005 | 560 | 0.0007 | +0.0002 |

**5건 전부 예외 없이 점수가 올랐다.** 추가한 내용에는 실제 관련성 판단에 쓰일 정보가 전혀 없는데도
점수가 오른다는 건, 이제 가설이 아니라 **인과관계로 확정**된 것 — cross-encoder(`Dongjin-kr/ko-reranker`)는
텍스트가 길수록(내용의 질과 무관하게) 더 높은 관련성 점수를 주는 편향이 있다.

**주의**: 절대적인 증가폭은 사례마다 다르다(882159는 +0.20, 884553은 +0.0002) — 원래 점수가
0에 가까울수록(883238, 884553) 절대 증가폭도 작다. 하지만 방향은 5/5 전부 일관되게 양(+)이라
"우연"으로 보기 어렵다.

**의미**: 앞서 검토했던 "형태소 분석기 도입"(BM25용)은 여전히 근거가 약하다 — 문제는 BM25가 아니라
cross-encoder에 있다. 반대로 처음에 제안했던 "요청 텍스트를 정형화/고정 길이로 통일"하는 방향은
이 결과로 힘을 얻는다 — 모든 사례의 `_case_text()` 길이를 통일하면(예: 고정 길이로 자르거나 패딩),
적어도 이 특정 편향(글 길이가 곧 관련성으로 오채점되는 것)은 구조적으로 제거된다. 다만 트렁케이션
길이를 얼마로 잡을지, 정보 손실(짧게 자르면 상세 요청 내용이 날아감)과의 트레이드오프는 별도로
검토해야 한다 — 다음 단계로 남겨둔다.

## 완화책 탐색 1 — 트렁케이션 길이(캡) 축소

실제 프로덕션 `case_text` 길이를 재보니(밀려난 사례 199~303자 vs 끌어올려진 사례 전부 336자 —
300자 캡에 걸려 동일) 앞서 "정정" 절의 원본/필러 실험에서 쓴 "212자 vs 560자"는 **틀린 수치였다**
— 그건 `request_body_text` 원문 길이였지, `_case_text()`가 실제로 잘라서 모델에 넣는 길이가
아니었다(300자 캡 때문에 promoted 4건은 이미 전부 336자로 수렴해 있었음). 정정한다.

`eval/case_text_cap_experiment.py`로 캡을 300(현재)/150/100/60으로 바꿔가며 재평가:

| cap | precision@5 | recall@5 | precision@10 | recall@10 |
|---|---:|---:|---:|---:|
| 300(현재) | 30.0% | 12.2% | 30.0% | 24.3% |
| 150 | 30.0% | 12.3% | **30.8%** | 25.0% |
| 100 | **32.5%** | 13.3% | 28.7% | 23.0% |
| 60 | 31.7% | 13.0% | **30.4%** | 24.2% |

(참고: 벡터 단독 baseline은 precision@5 33.3%, precision@10 27.1%)

**cap=60이 유일하게 baseline(300) 대비 4개 지표 전부 같거나 개선된 값**이다 — precision@5
+1.7%p, precision@10 +0.4%p, recall도 둘 다 소폭 개선. cap=100은 precision@5는 가장 좋지만
precision@10이 오히려 300보다 나빠져서(-1.3%p) 트레이드오프가 남는다.

**한계**: 캡을 줄이는 건 정보를 버리는 방식이다 — 사례 텍스트를 60자까지만 보므로 자재 종류·특수
요청사항 같은 세부 정보가 지금보다 더 많이 잘려나간다. 근본 해결이 아니라 완화책.

## 완화책 탐색 2 — 통계적 de-biasing (실패)

정보를 버리지 않고 편향만 통계적으로 제거하는 방법을 시도했다: 같은 쿼리의 후보 풀 안에서
"CE 점수 vs 텍스트 길이"의 1차 선형회귀를 구해, 그 관계로 설명되는 부분을 뺀 잔차로 재정렬.

**쿼리별(로컬) 회귀** (`eval/ce_length_debias_experiment.py`, 쿼리당 후보 20건으로 회귀 추정):

| 지표 | CE 원점수 | 길이 de-bias | 변화 |
|---|---:|---:|---:|
| precision@5 | 30.0% | 28.3% | -1.7%p |
| precision@10 | 30.0% | 27.1% | -2.9%p |

**전역 회귀** (`eval/ce_length_debias_global_experiment.py`, 24개 쿼리 × 20건 = 480쌍을 합쳐
회귀식 하나로 추정: `score = 0.000445 × length - 0.0256`):

| 지표 | CE 원점수 | 전역 de-bias | 변화 |
|---|---:|---:|---:|
| precision@5 | 30.0% | 29.2% | -0.8%p |
| precision@10 | 30.0% | 26.7% | -3.3%p |
| recall@10 | 24.3% | 20.7% | -3.6%p |

**둘 다 전 지표 악화 — de-biasing은 실패했다.** 로컬 회귀는 표본(쿼리당 20건)이 작아 과적합
가능성이 크다고 봤고, 표본을 20배(480쌍)로 늘린 전역 회귀도 여전히 악화됐다(정도는 덜함).
전역 회귀의 기울기(`0.000445`)가 매우 작다는 건 애초에 길이가 CE 점수 분산에서 차지하는 비중이
크지 않다는 뜻인데도 성능이 떨어졌다 — 이는 **실제 데이터에서 텍스트 길이와 진짜 관련성이 어느
정도 겹쳐 있어서**(상세히 쓴 사례가 우연히 정말 더 잘 맞는 경우도 있음), 편향만 깔끔하게 분리해
제거하는 게 이 표본 규모에서는 어렵다는 뜻으로 해석한다.

## 결론 — 지금까지 검증된 최선은 cap=60

| 시도 | 결과 |
|---|---|
| BM25 `b` 파라미터 조정 | 효과 없음 (BM25가 최종 순위에 애초에 무관했음, 이 eval 범위 한정) |
| 캡 축소 (300→60) | **전 지표 소폭 개선 — 유일하게 순수 개선된 방법** |
| 통계적 de-biasing (로컬/전역) | 둘 다 전 지표 악화 |

`_case_text()`의 트렁케이션 길이를 300 → 60으로 낮추는 것을 실전 반영 후보로 제안한다. 다만
정보 손실 트레이드오프가 있고, 표본(쿼리 24개) 자체가 작아 이 개선폭이 노이즈인지 재현 가능한
패턴인지는 추가 검증이 필요하다.

**남은 검증 항목**: BM25의 진짜 효과는 여전히 미검증 상태다 — 이 eval의 `pool.json`이 벡터 top-20만
담고 있어 `RERANK_POOL=20`과 크기가 같아서 RRF가 원천적으로 아무것도 걸러내지 못했다(위 "정정"
절 참고). 프로덕션은 벡터 후보 40개 중 20개로 추리므로, 이를 제대로 검증하려면 pool을 벡터
top-40 기준으로 재구축(21~40위 재라벨링)해야 한다 — 다음 조사로 이어간다.

## BM25의 진짜 효과 검증 — pool을 벡터 top-40으로 확장

위 "결론" 절에서 밝힌 대로, 기존 eval은 `pool.json`이 벡터 top-20만 담고 있어 `RERANK_POOL=20`과
크기가 같아서 BM25/RRF가 원천적으로 아무것도 걸러내지 못했다. `eval/extend_pool_top40.py`로
프로덕션과 동일한 `vector_candidate_pool=40` 기준까지 pool을 확장했다.

**확장 방법**: 24개 쿼리 각각에 대해 벡터 검색을 top-40까지 다시 실행해, 기존 pool에 없던
21~40위 후보 456건을 새로 찾아 규칙 기반 `suggested_relevant`(평수 ±5평, 인접 권역, 공종 1개
이상 겹침 — `build_pool.py`와 동일 기준)로 라벨링했다. 규칙 기반 결과 456건 중 84건이 relevant로
추정됐다. `flag_review_rows.py`로 재검토 필요 행을 다시 추려보니 456건 중 140건(31%)이 플래그됐지만,
**이번엔 비용 대 효과를 고려해 사람이 직접 재검토하지 않고 규칙 기반 라벨을 그대로 신뢰했다** —
기존 1~20위 라벨(915건, 187건 사람 검토 완료)과 달리 **이 21~40위 확장분(456건)은 사람 검토를
거치지 않은 상태**라는 걸 명시한다. 이전 검토 라운드에서 플래그된 행의 약 25%가 실제로 뒤집힌
전례가 있어(위 `docs/IMPLEMENTATION_LOG.md` 2-7 참고), 이 456건에도 비슷한 비율의 라벨 노이즈가
있을 수 있다.

**결과** (`eval/retrieval_eval_top40.py`, `EstimateEngine._hybrid_rerank()`를 실제 프로덕션 설정
그대로 호출 — `RERANK_POOL=20`이 이번엔 진짜로 40개 중 20개를 필터링함):

| 지표 | 벡터 단독(top-40) | 하이브리드(40→20→CE, 실제 설정) | 변화 |
|---|---:|---:|---:|
| precision@5 | 33.3% | 32.5% | -0.8%p |
| precision@10 | 27.1% | **31.2%** | **+4.2%p** |
| recall@5 | 11.5% | 10.2% | -1.3%p |
| recall@10 | 17.8% | 18.7% | +1.0%p |

(recall이 이전 eval보다 전반적으로 낮아진 건 정상이다 — pool이 40개로 커지면서 relevant 총 개수도
늘어 "pool 내 recall"의 분모가 커졌을 뿐, 코퍼스 자체가 바뀐 게 아니다.)

**이전(잘못된 top-20 전용) 결과와 비교**:

| | precision@5 변화 | precision@10 변화 |
|---|---:|---:|
| 이전(BM25가 무의미했던 eval) | -3.3%p | +2.9%p |
| 진짜 40→20 필터링 | **-0.8%p** | **+4.2%p** |

**결론**: BM25/RRF가 실제로 후보를 걸러내는 프로덕션 조건에서 재평가하니, precision@5 손실은
4분의 1 수준으로 줄고(-3.3%p → -0.8%p) precision@10 개선폭은 오히려 더 커졌다(+2.9%p → +4.2%p).
즉 BM25는 무의미한 게 아니라 — 이전 eval 설계 결함(pool 크기 = RERANK_POOL) 때문에 그 효과를
측정할 수 없었을 뿐이고, 제대로 측정하니 하이브리드 검색이 이전 추정보다 더 낫다는 신호로
나타났다. 다만 21~40위 라벨의 사람 검토가 빠져 있다는 한계는 남아있다.

## 1차 결론(사람 검토 전) — 캡=60 + 진짜 40→20 파이프라인 조합

> **주의**: 이 절의 수치는 21~40위 라벨을 사람이 검토하기 *전*(규칙 기반 그대로) 값이다.
> 검토 후 일부가 뒤집히면서(아래 "사람 검토 사고와 복구" 절 참고) 수치가 달라졌다 — 다만
> 방향(캡=60이 벡터 단독을 이긴다)은 검토 후에도 그대로 재확인됐다. 최종 검증된 수치는 아래
> "사람 검토 사고와 복구" 절의 표를 참고할 것.

두 완화책(캡 축소, 진짜 40→20 BM25 필터링)을 각각 따로 검증했으니, 합쳤을 때 어떤지
`eval/combined_cap60_top40_experiment.py`로 확인했다 — pool은 벡터 top-40 확장분을 쓰고,
`_hybrid_rerank()`와 동일한 흐름(BM25+RRF로 40→20 필터 → cross-encoder)에 `_case_text()`
캡만 60으로 바꿔서 재현.

| cap | precision@5 | recall@5 | precision@10 | recall@10 |
|---|---:|---:|---:|---:|
| 300(현재 프로덕션) | 32.5% | 10.2% | 31.2% | 18.7% |
| **60** | **35.8%** | **12.4%** | 30.8% | **20.0%** |

(벡터 단독 baseline: precision@5 33.3%, precision@10 27.1%)

**precision@5(35.8%)가 처음으로 벡터 단독(33.3%)을 넘어섰다.** precision@10(30.8%)도 벡터
단독(27.1%) 대비 +3.7%p 높고, recall@5/recall@10도 둘 다 개선됐다. cap=300 대비로는 4개 지표
중 3개 개선(p@5 +3.3%p, r@5 +2.2%p, r@10 +1.3%p), 나머지 하나(p@10)는 -0.4%p로 사실상 동일.

**이 조사 전체의 결말**: 최초 발견한 "혼재된 결과"(precision@5는 나쁘고 precision@10만 좋음)는
실제 개선 효과가 없어서가 아니라, **두 가지 설계 결함이 겹쳐서 생긴 착시**였다 —
① 캡이 300으로 너무 넉넉해서 cross-encoder의 텍스트 길이 편향이 그대로 드러났고,
② pool이 벡터 top-20뿐이라 BM25/RRF가 원래 하려던 필터링을 전혀 못 하고 있었다.
둘 다 바로잡고 나서야 하이브리드+리랭킹이 벡터 단독보다 명확히 나은 결과를 낸다는 게 드러났다.

**남은 한계**: 21~40위 라벨 456건 중 140건(31%)은 사람 검토 없이 규칙 기반 라벨을 그대로 썼다
(위 "BM25의 진짜 효과 검증" 절 참고) — 이 결론은 그 노이즈를 감안하고 봐야 한다. 프로덕션에
캡=60을 반영하기 전에, 최소한 이 140건 중 일부라도 사람이 검토해 결론이 라벨 노이즈 때문에
뒤집히지 않는지 확인하는 게 안전하다.

## 사람 검토 사고와 복구 — 평가 방법론 자체의 함정

위 140건을 실제로 사람이 검토하는 과정에서 **두 가지 방법론 버그**가 났고, 둘 다 발견해서
바로잡았다. 결과에 실제로 영향을 준 사고라 그대로 기록한다.

**사고 1 — 라벨링 기준에 순위를 넣은 것 자체가 순환 논리였다.** `top3_but_zero`(검색 엔진이
1~3위로 추천했는데 규칙은 탈락시킨 경우) 판단 기준으로 "top-3면 관련성 신호로 봐도 된다"고
안내했는데, 이건 **벡터 검색 자신의 순위를 근거로 벡터 검색이 맞았다고 라벨링하는 순환**이다.
실제로 이 기준으로 71건을 반영한 뒤 재평가하니 벡터 단독 precision@5가 33.3% → **45.8%로
급등**했고, 하이브리드는 오히려 벡터 단독보다 −9.2%p 뒤처지는 것으로 나와 지금까지의 결론이
완전히 뒤집혔다.

**사고 2 — "신규(21~40위)"를 구분하는 필터 자체가 틀렸다.** 검토 대상 140건을 추릴 때
`bm25_rank`가 비어있는 행을 "신규"로 간주했는데, **원래 1~20위 중에도 BM25 top-20에는
못 든(벡터로만 찾은) 행은 애초에 `bm25_rank`가 비어있다.** 그래서 이미 첫 라운드(915건)에서
사람이 검증까지 끝낸 오래된 1~20위 행 64건이 실수로 이번 재검토 대상에 다시 섞여 들어갔고,
그중 일부(28건)가 새 기준(순위 기반 관대함)으로 다시 라벨링되면서 이미 확정됐던 ground truth를
덮어썼다. 사고 1의 급등(45.8%)은 사실상 전부 이 오염 때문이었다 — 신규 21~40위 행은 정의상
`vector_rank`가 21~40이라 애초에 `top3_but_zero`(vector_rank≤3) 조건에 해당할 수가 없다.

**복구**: 확장 전 백업(`pool.json` 915건 원본)과 실제 사람이 편집한 `review_priority.csv`(140건)를
`(query_id, article_id)` 키로 대조해서, 원본 915건에 이미 있던 64건(오염분)과 진짜 신규
76건을 분리했다. `pool.json`을 915건 백업으로 복구하고 `extend_pool_top40.py`를 재실행해
21~40위 456건을 다시 생성한 뒤(결정론적이라 이전과 동일하게 재현됨), 진짜 신규 76건에 대한
사람 검토 결과(44건 반영)만 다시 적용했다.

**복구 후 재검증 결과** — 벡터 단독 precision@5가 정확히 원래 값(33.3%)으로 돌아왔고, 오염
전 첫 결론과 방향이 일치하는 걸 확인했다:

| cap | precision@5 | recall@5 | precision@10 | recall@10 |
|---|---:|---:|---:|---:|
| 벡터 단독(top-40) | 33.3% | 10.0% | 27.1% | 15.7% |
| 하이브리드 cap=300 | 32.5% | 8.8% | 34.2% | 18.7% |
| **하이브리드 cap=60** | **35.8%** | **10.6%** | **31.7%** | **18.2%** |

**cap=60이 벡터 단독 대비 4개 지표 전부 개선**(p@5 +2.5%p, r@5 +0.6%p, p@10 +4.6%p,
r@10 +2.5%p) — 오염 사고 이전 첫 결론(캡=60 조합이 벡터 단독을 이긴다)과 방향이 동일해서,
이 개선이 우연이 아니라는 확신이 더 커졌다. `retrieval_eval_top40.py`(캡=300, 진짜 BM25
필터링만)의 precision@10 개선폭도 오염 복구 후 +4.2%p → **+7.1%p로 오히려 더 커졌다.**

**교훈**: TREC 스타일 pooling에서 "검색 순위를 보고 판단 기준을 완화"하는 건 잘 알려진 함정
(judge가 순위에 영향받으면 그 순위를 매긴 시스템이 자동으로 유리해짐)인데, 이번에 직접 그
함정에 걸렸다가 결과가 비정상적으로(원인 없이) 급등하는 걸 보고 원인을 추적해서 잡아냈다.
"신규 vs 기존"을 나이브한 필드 값(`bm25_rank` 존재 여부)으로 구분한 것도 원인이었다 — 이런
집합 구분은 명시적인 키 대조(백업과의 diff)로 검증해야 한다는 것도 확인.

## 664건 추가 후 재검증 (2026-09-02) — 코퍼스 성장이 검색 품질에 준 영향 + precision@15 추가

**pool 갱신**: `build_pool.py`를 그냥 재실행하면 기존에 사람이 검토해둔 라벨이 전부
`suggested_relevant`로 리셋되는 문제가 있어(이 파일에 기록되지 않았던, 이번에 새로 발견한
설계 결함 — `eval/refresh_pool.py`로 해결), 기존 라벨을 보존하면서 코퍼스 성장분만 반영하는

`suggested_relevant`를 그대로 label로 쓴 경우)와 검토 후를 같은 pool로 나란히 돌려봤다.

| 지표 | 검토 전(규칙만) | 검토 후(사람 반영) | 차이 |

| precision@10 (벡터) | 27.5% | 33.8% | +6.3%p |

| recall@5/10 | — | — | +0.9~1.8%p |

검토 전/후로 6~8%p씩 차이가 났다 — 검색 시스템이 달라진 게 아니라 규칙 기반 `suggested_relevant`
가 애매한 경계 케이스(주로 "검색이 1~3위로 추천했는데 규칙이 탈락시킨" 경우)를 상당수 잘못
판정하고 있었다는 뜻이다. 이 세션 앞부분의 "사람 검토 사고"(순환 논리로 71건이 잘못 반영돼
precision@5가 45.8%까지 튀었던 사고)와 근본 원인은 다르지만 — **"라벨링 없이 규칙만 믿으면
안 된다"는 같은 교훈을 다시 확인한 셈**이다. 이후 모든 수치는 검토 후(최종) 라벨 기준이다.

**precision@15 추가 — 이전까지의 @5/@10 지표엔 없던 사각지대**: `EstimateEngine`의
실제 최종 후보 수는 `TOP_K=15`(`app/domain/estimate_engine.py:28`)인데, 지금까지 이 문서의
모든 실험은 @5/@10만 봤다 — 즉 **프로덕션이 실제로 쓰는 깊이를 한 번도 직접 측정한 적이
없었다.** 이번에 `eval/retrieval_eval.py`의 `K_VALUES`에 15를 추가했다.

| 지표 | 벡터 단독 | 하이브리드+리랭킹 | 변화 |
|---|---:|---:|---:|
| precision@5 | 42.5% | 36.7% | -5.8%p |
| recall@5 | 13.5% | 11.3% | -2.2%p |
| precision@10 | 33.8% | 38.8% | +5.0%p |
| recall@10 | 21.0% | 23.8% | +2.9%p |
| **precision@15** | **32.2%** | **36.9%** | **+4.7%p** |
| **recall@15** | **29.7%** | **33.3%** | **+3.6%p** |

**결론**: precision@5만 보면 하이브리드+리랭킹이 손해(-5.8%p)로 보이지만, 프로덕션이 실제로
작동하는 깊이(top-15)에서는 precision·recall 둘 다 뚜렷하게 개선된다(+4.7%p, +3.6%p). top-5
구간의 손실은 실사용 범위 밖의 현상이라 이 결과만으로 하이브리드+리랭킹을 끌 근거는 없다 —
오히려 지금까지 @5/@10만 보고 "혼재된 결과"라고 판단해온 것 자체가 측정 범위가 프로덕션과
안 맞았던 것일 수 있다는 걸 이번에 알게 됐다.

**참고 — 크롤링 반영 전(2026-08-30) 대비**: 이 문서 상단 초기 실험(L33-34) 대비 벡터 단독
precision@5는 33.3% → 42.5%(+9.2%p) 개선됐지만, recall@5는 14.9% → 13.5%(-1.4%p) 소폭
하락했다(원인은 미조사 — pool 크기가 922건으로 커지며 relevant 분모가 늘었을 가능성).

**한계**: 이번 재검증은 이 문서 앞부분에서 확정한 `cap=60` 완화책이나 `top-40 확장 pool`은
같이 적용하지 않은, 현재 프로덕션 기본 설정(cap=300, pool=top-20) 기준 수치다 — 두 완화책을
664건 반영 후 코퍼스에도 다시 적용해서 @15까지 같이 보는 건 다음 조사로 남겨둔다.

**이 precision 수치들이 30~40%대인 게 왜 정상인가 (버그 아님)**: 처음 보면 낮아 보일 수 있는데,
두 가지 설계 선택 때문에 애초에 100%에 가까운 수치가 나올 수 없는 구조다.

1. **정답(label) 기준 자체가 3조건 동시 충족을 요구한다** — `_suggested_relevant()`(및 사람
   검토 기준)는 평수 ±5평, 인접 지역, 공종 최소 1개 겹침을 **전부** 만족해야 relevant=1이다.
   느슨한 "대충 비슷한 사례"가 아니라 실제 참고할 만한 엄격한 기준이라 애초에 통과율이 낮다.
2. **베이스라인(벡터 단독)이 지역/평수 필터링을 전혀 안 한다** — pool을 만들 때 벡터 검색은
   순수 텍스트 유사도만 보고 top-20을 뽑는다. 그래서 서울 쿼리에 부산 사례가 텍스트만
   비슷해서 올라오는 경우가 흔한데, 이게 label=0으로 그대로 깎인다. 애초에 이 "필터 없는
   벡터 검색의 약점"을 보완하려고 하이브리드+리랭킹을 붙인 것이다.

즉 33~43% 수준의 precision@5는 "검색이 형편없다"가 아니라 "정답 기준이 엄격하고 베이스라인이
필터를 안 쓴다"는 이 eval의 설계에서 나오는 자연스러운 범위다. 이 문서 전체에서 봐야 할 신호는
절대 수치가 아니라 **벡터 단독 대비 하이브리드+리랭킹이 어느 방향으로, 얼마나 움직이는가**다 —
그 상대적 개선폭(+4.7%p @15)이 이 조사의 실제 결론이다. 24개 쿼리라는 표본 크기도 절대 수치의
신뢰구간을 넓히는 요인이라, 어느 쪽으로도 "정확히 이 값"이라고 못박기보다는 방향성 지표로
읽는 게 맞다.

## 재현 방법

```bash
python -m eval.retrieval_eval                  # 벡터 단독 vs 하이브리드+리랭킹 (기본 b=0.75)
python -m eval.bm25_b_variant_experiment        # BM25 b=0.75 vs b=1.0 비교 (1차 원인 분석, 이후 정정됨)
python -m eval.vector_ce_only_experiment        # BM25 완전 제거, 벡터+CE만 비교 (정정 근거)
python -m eval.ce_length_bias_experiment        # 필러 패딩으로 CE 길이 편향 인과관계 확정
python -m eval.case_text_cap_experiment         # 트렁케이션 길이(캡) 스윕 — 완화책 탐색
python -m eval.ce_length_debias_experiment      # 쿼리별 선형회귀 잔차 de-biasing (실패)
python -m eval.ce_length_debias_global_experiment  # 전역 선형회귀 잔차 de-biasing (실패)
python -m eval.extend_pool_top40                # pool을 벡터 top-40까지 확장 (1회성, pool.json 갱신)
python -m eval.retrieval_eval_top40             # 진짜 40->20 필터링으로 BM25 효과 재검증
python -m eval.combined_cap60_top40_experiment  # 캡=60 + 진짜 40->20 파이프라인 조합 (최종 결론)
python -m eval.refresh_pool                     # 코퍼스 성장 반영, 기존 사람 라벨 보존하며 pool 갱신
python -m eval.flag_review_rows                 # 갱신된 pool 중 검토 필요 행 추출
python -m eval.apply_review_labels              # 사람이 review_priority.csv에서 수정한 라벨 반영
python -m eval.retrieval_eval                   # precision@15/recall@15 포함 (2026-09-02부터)
```

코퍼스나 라벨을 바꾸지 않는 한 결과는 결정론적이다(같은 pool, 같은 라벨, 같은 벡터 후보 순서).
